Bug analysis / CPU_BOUND

滑动窗口在 inline 回退后失去完成信号

当 worker executor 拒绝 CPU 任务时，任务会在调用线程内完成；但滑动窗口只等待 completion service 写入的队列事件。因此“任务完成”不再等于“窗口获知完成”。

Confirmed两任务、窗口为一、worker 必拒绝时，可稳定复现第二个 future 永久 PENDING。
01 / Failure path

复现：任务 1 完成，任务 2 永远不提交

条件：CPU_BOUND，parallelism = 1，两个任务，worker executor 已关闭。首个任务触发 inline fallback；第二个任务只能等待窗口收到首个完成事件后才会提交。

02 / Cause

同一个批次存在两套完成协议

执行路径future 如何创建终止时发生什么窗口是否前进
普通 worker 提交ListenableCompletionServicelistener 将 future 写入 blockingQueue是
CPU inline 回退Futures.submit(..., directExecutor())future 仅变为完成状态否

当前职责分裂

完成通知只被认为是 completion service 的副作用。回退分支绕过 service 后，调用方仍等待该 service 的队列。

应有职责

完成通知应绑定到任务 future 本身：无论由哪个 executor 运行，同一 future 终止时都发布一个完成事件。

03 / Target design

统一为“先监听，再选择执行位置”

把 CPU 回退放进 ListenableCompletionService 的提交过程。它只创建一次任务 future，并且在尝试 worker 执行前注册完成 listener；若拒绝，再用 direct executor 运行同一个 future。

Required invariant每个进入滑动窗口的任务 future，在终止时恰好向完成队列发布一次事件。
private ListenableFuture<V> submitCpuTask(Callable<V> task) {
    ExecutionPhaseHintFuture<V> future =
            ExecutionPhaseHintFuture.create(task, phaseObserver);
    future.addListener(() -> completionQueue.add(future), directExecutor());

    try {
        executor.execute(future);
    } catch (RejectedExecutionException rejected) {
        directExecutor().execute(future); // 运行同一个已监听 future
    }
    return future;
}
04 / Regression test

把缺失的窗口补充路径纳入测试

原测试只有单任务，remaining == 0，不会调用 submitRemaining()。回归测试必须让 inline 任务的完成事件真正驱动下一次提交。

// worker 已关闭，保证每个任务都走 CPU inline fallback
BatchExecutionContext context = context(2, 1, TaskType.CPU_BOUND);
AsyncBatchResult<Integer> batch = executor.submitAll(Arrays.asList(() -> 1, () -> 2));

assertThat(batch.getResults().get(0).get(1, SECONDS)).isEqualTo(1);
assertThat(batch.getResults().get(1).get(1, SECONDS)).isEqualTo(2);
assertThat(batch.getSubmitCanceller().get(1, SECONDS)).isNotNull();
