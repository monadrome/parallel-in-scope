偶发测试失败分析：外层 future 的值断言 vs 取消级联的竞态

测试：ParallelTaskGroupTest#outerBatchCancellationPropagatesIntoGroupAsGroupCancellation
现象：单独跑 5/5 通过；全量 mvn test 负载下偶发报 CancellationException: Task was cancelled（line 651）。

1. 测试在做什么

外层 batch（1 个任务）
  └─ 任务内部：构建并提交一个嵌套 group（成员 sleep 10s），然后阻塞等 group 收敛，
     返回 group 的 completionReason 名字（"CANCELED"）
主线程：等 group 建好后，取消外层 token（outerToken.cancel(true)）
断言①：外层 future.get() == "CANCELED"   ← 问题在这行（line 651）
断言②：group 收敛原因 == CANCELED
断言③：成员 outcome == GROUP_CANCELED

2. 关键机制：Guava cancel 的顺序

外层 token 的 futureToken 通过 setFuture(failFastFuture) 委托出去。 对 Guava 33.6.0 的 AbstractFuture.cancel(boolean) 字节码确认（javap）：

casValue(...) 成功之后：
  complete(this, mayInterrupt)   // ← 先完成自己，同步触发自己的 listeners
  然后才 cancel delegate          // ← 之后才取消委托链（failFastFuture → allAsList → 任务 future）
结论：token 取消时，"子 scope 的传播" 先于 "绑定任务的硬取消"。 这是框架的刻意设计（与 bind() 里"先提交状态、再级联取消"一致），不是 bug。

3. 竞态时序图

主线程执行 outerToken.cancel(true) 时，外层 worker 线程正阻塞在任务里的 group.completionFuture().get()。两个线程之后的动作形成竞争：

顺序
主线程（cancel 级联，全程同步）
worker 线程（外层任务）
1
transitionTo(MUTUAL_CANCELED) 提交状态
阻塞在 completionFuture.get()
2
futureToken 先 complete → group 传播 listener 触发
→ group token PROPAGATING_CANCELED → 成员取消 → 收敛
→ completion.set(result) ── unpark worker ──▶
被唤醒，等待被调度上 CPU…
3 ⚡
路径A：继续取消 delegate 链 → 外层任务 future.cancel(true)
路径B：get() 返回 → 任务 return "CANCELED" → future.set("CANCELED")
第 3 步是两个线程对同一个 future 的 CAS 竞争：
主线程赢 → future 被硬取消 → 断言①的 get() 抛 CancellationException（偶发失败）
worker 赢 → future 正常完成带值 "CANCELED" → 测试通过（常见情况）

4. 为什么单独跑总过、全量负载偶发挂

单独跑 / 空闲机器全量 mvn test
worker 唤醒后上 CPU立刻（核空闲，futex 唤醒直接调度）可能延迟数毫秒（GC、其他测试的 timer/executor 线程占核）
主线程第 3 步耗时固定只有几微秒（同步 listener 链）
结果worker 几乎必胜worker 偶尔来不及 → 断言①炸

补充：即使 worker 是被 interrupt 唤醒的（get() 抛 InterruptedException），测试里的 while(true) 会重试并成功拿到 group 结果——但此刻 cancel 已提交，set() 无效，future 仍是 cancelled，断言①照样失败。

5. 根因定性

这是测试断言写错了对象，不是框架 bug。 断言①断言了一个框架从未保证的行为："被 token 绑定的 future 在取消后还能正常返回值"。 框架保证的是：取消时子 scope 先收敛、绑定的工作后被取消。 测试的真正主题——group 归因——由断言②③覆盖，它们不涉竞态。

6. 修复方案（test-only）

推荐：删掉断言①对 future 值的依赖，改为用 AtomicReference 记录任务内部观察到的 group 结果（任务 return 前写入），主线程断言这个 reference。同步手段（groupBuilt latch + completionFuture().get()）不变，竞态消除，断言语义不变。

任务内部：  observed.set(group.completionFuture().get().completionReason().name()); return null;
主线程：    await until observed != null；assertThat(observed.get()).isEqualTo("CANCELED");
            （断言②③保持不变）

不推荐：对 get() 容忍 CancellationException（削弱断言）；或改框架 cancel 顺序（当前顺序是正确设计，不动）。
