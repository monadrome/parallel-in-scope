Axiom Drift

The execution kernel holds up. What has drifted is the surface the user actually touches: two options that do nothing unless you happened to wire your own thread pool a particular way, a scope whose close() does not close anything, a typed key that only checks raw types, and a group that reports failure by returning normally.

How this was checked

Every claim below is marked with its provenance, because the two kinds are worth very different amounts.

probe means a throwaway harness drove the public API only and printed the contradiction. Six such claims were run; one hypothesis I held going in was disproved by its own probe and has been struck from this report rather than softened.

code reading means static reading plus grep, with a path:line anchor. These are structural facts (what is public, what is unreachable, what allocates), not behavioural predictions.

This review deliberately does not restate reports/defect-analysis-2026-09-10.md. Those five defects are reproduced by verification/defect-repro/run.sh and stand on their own; findings here are new ground, and where they touch a known defect it is called out.

The disproved one, for the record. I expected HeuristicPurger to spawn a scheduler thread even with purge disabled (which is the default). It does construct the executor eagerly — but Executors.newSingleThreadScheduledExecutor starts no thread until the first task, so the thread count really is zero. No finding.
Tier A

Nine places the code contradicts its own axioms

design/first-principles.md is unusually explicit for a library this size, which makes it a real test instrument: each finding below names the axiom it fails, not a matter of taste.

A1

Closing a scope does not close anything — user code outlives the try-block

structural probe Axiom 1 · 作用域关闭时其内工作必然终态

Axiom 1 promises that when a scope closes, the work inside it is necessarily terminal. Both closers break that promise: TaskGroup.close() cancels and returns, and cancellation is only a best-effort interrupt — user code that does not cooperate keeps running on the pool. GlobalPar.close() likewise rejects new work and returns without waiting.

TaskGroup.java:145 — public void close() { if (!completion.isDone()) cancel(); }

Measured with a member that ignores interrupts, inside try-with-resources:

7 scope-close-does-not-join : user code still running right after close()? true
   user code actually ended 299ms AFTER the try-with-resources block exited

This is the gap between this library and StructuredTaskScope, whose close() joins by contract. Today the syntax that looks like a structured scope gives a weaker guarantee than the axiom states, and no javadoc on close() says so.

Direction Either make close() cancel-then-join (the axiom as written, with a bounded grace period so a rogue task cannot hang shutdown forever), or keep the non-blocking close and amend Axiom 1 to "terminal or abandoned with cancellation requested" — and say it on close(). The first is the honest reading of the project's own stated position; whichever you pick, the doc and the code must agree, because this one sentence is what the library sells.
A2

A group whose member threw completes successfully

footgun probe Axiom 2 · 忘记处理失败

convergeIfTerminal() always calls completion.set(result) — never setException. So completionFuture().get() returns normally even when every member failed, and the only trace is a field on the result the caller has to remember to read.

4 group-failure-visibility : get() RETURNED NORMALLY, outcome=MEMBER_CANCELED failedTask=boom
  -> a caller who does not inspect outcome() silently loses the failure

"Outcome is data, not an exception" is a deliberate and defensible decision — TaskBatchResult makes the same call. But Axiom 2 says the library's job is to make forgetting either impossible or conspicuous, and right now forgetting is neither: there is no orThrow(), no throwIfFailed(), and nothing that a reviewer would notice missing at a call site. Note the probe also re-confirms defect #5 from the September 10 report — a lone failing member reads MEMBER_CANCELED, not USER_FAILURE.

Direction Add one terminal accessor on TaskGroupResult that throws the recorded failure (orThrow() / successfulOrThrow()), and mirror it on TaskBatchResult. Data stays the default; the loud path becomes one call away instead of unavailable. This costs no new concept — it is a reader over the snapshot that already exists.
A3

rejectEnqueue — on by default — does nothing unless the user picked one specific queue

inert option probe Axiom 3 · 安全性优先于表达力

BatchOptions and TaskOptions both expose rejectEnqueue(boolean), defaulting to true. The only code in the library that reads it is SmartBlockingQueue.offer — a public class the library never instantiates. Register a pool built with a plain LinkedBlockingQueue and the option is a no-op, silently.

SmartBlockingQueue.java:66 — the sole reader of unit.rejectEnqueue() and of taskType() == CPU_BOUND for queue skipping

Same batch, same options (IO_BOUND + rejectEnqueue(true)), only the queue differs:

2 rejectEnqueue(true)+IO_BOUND honoured?
  plainLinkedBlockingQueue rejections=0   SmartBlockingQueue rejections=3
  -> option is SILENTLY INERT unless the user picked SmartBlockingQueue

TaskType is half-affected: its inline-fallback-on-rejection behaviour works with any executor, but its queue-skipping behaviour has the same dependency. So the same enum means one thing or two things depending on plumbing the option type never mentions.

Direction Pick one. Either GlobalPar.Builder.register installs the smart queue itself (owning the mechanism the option promises), or it validates at build() and refuses — or at minimum warns once — when a registered pool cannot honour an enqueue policy. An option that is documented, defaulted to true, and inert is exactly the "easy to misuse capability" Axiom 3 says to withhold rather than ship.
A4

Pre-wrapping your own pool silently disables purge and deadlock detection

silent degradation probe Axiom 2 · 结构性保证或显眼

Two features gate on suppliedExecutor instanceof ThreadPoolExecutor. A user who registers MoreExecutors.listeningDecorator(pool) — a natural thing to do in a Guava codebase, and a shape ExecutorRuntime explicitly anticipates — fails both checks: blockingRisk falls back to UNKNOWN and the purge observer becomes a no-op.

ExecutorRuntime.java:71 detectRisk · GlobalPar.java:358 bindPurgeObserver — both test the wrapper, not the pool inside it

Identical topology (a batch nesting a batch on the same pool), registered raw versus decorated:

3 executor self-loop (same pool nested in itself) detected?
  raw TPE=true   listeningDecorator(TPE)=false
  -> DETECTION SILENTLY LOST when the user pre-wraps their pool

The deadlock detector is the library's answer to its most dangerous failure mode — a bounded pool nested inside itself. Losing it to a wrapper, with no diagnostic, is the worst possible failure shape for a safety feature.

Direction Unwrap before classifying. Guava's decorator does not expose its delegate, so register should accept the physical pool and do its own listening adaptation (ExecutorRuntime already handles both cases), and reject or warn on an executor it cannot see through. Detection that silently downgrades is worse than detection that refuses to start.
A5

TaskKey's type safety is raw-type only — it permits heap pollution

type safety probe §三 · 类型安全下沉到键

TaskKey captures a full TypeToken, then both resolution sites throw that fidelity away by comparing getRawType(). A key claiming List<Integer> resolves a member registered as List<String>: both raw types are List.

TaskGroup.java:132 and CompletedTaskValues.java:47 — key.resultType().getRawType().isAssignableFrom(member.resultType.getRawType()) 
1 generic-key-check : ACCEPTED by future(key), blew up later at element access:
  java.lang.ClassCastException: class java.lang.String cannot be cast to class java.lang.Integer

The failure surfaces far from the mistake — at element access, in user code, with a stack trace that names neither the key nor the group. The stated reason keys exist at all is "type safety sunk into the key"; for every generic result type, which is most of them, that safety is currently nominal. It also weakens the invokeAll rejection in the idea graveyard, which leans on this exact property.

Direction TypeToken already answers this correctly: replace both checks with key.resultType().isSupertypeOf(member.resultType), which keeps the intended "a key may claim a supertype" rule and rejects the incompatible-generic case. Small, local, and it makes the documented guarantee real. If the v0.3 proposal to delete TaskKey in favour of returned TaskFuture<T> lands, this disappears instead — that plan is strictly stronger here, since the compiler does the work.
A6

A mistyped task name turns a cancellation checkpoint into a no-op

footgun probe Axiom 2 · 忘记 = 不可能或显眼

Checkpoints.checkpoint(taskName, lean) compares the argument to the current unit's name and returns silently when they differ — and again when there is no enclosing scope at all. So the one API a user calls to make long-running work cancellable fails open on a typo, on a renamed task, on a copy-pasted loop body, and on being called one frame too far out.

Checkpoints.java:47-56 — if (taskName == null || !taskName.equals(unit.name())) return; 
5 checkpoint-name-matching : wrongName=NO-OP(silent) rightName=threw
  -> a typo'd or refactored task name disables cooperative cancellation without a word

The name parameter earns nothing here. The framework's own pre-run call passes the unit's own name, so it always matches; the only behaviour the parameter can produce is the silent-skip that hurt the probe.

Direction Make the no-argument form the primary API (Checkpoints.checkpoint(), checking the current scope unconditionally, like rawCheckpoint already does), and have the framework call the internal token check directly. If a name-scoped variant survives at all, a mismatch should throw IllegalStateException — "you are not in the task you think you are in" is a bug, not a reason to skip a safety check.
A7

The deadline is enforced only by a timer thread — checkpoints never look at it

timing code reading §二 · deadline 是端到端预算

checkCancellationToken reads token.state() and nothing else. The token carries deadlineNanos() and remaining(), yet no checkpoint compares them. A task therefore stays "not cancelled" for as long as the timer thread is late — GC pause, busy scheduler, or a cached-pool thread yet to be created.

Checkpoints.java:494-502 · CancellationToken.java:134-139 (the already-expired case is defect #4 in the September 10 report)

This is the missing second line of defence behind that known defect: an expired deadline currently depends entirely on a scheduled action having run. Reading the clock at every checkpoint makes expiry a property of time rather than of scheduling — and the machinery is already in place.

Direction Treat deadlineNanos() <= System.nanoTime() as cancelled inside checkCancellationToken, and derive default waits from token.remaining() so checkGet(future) and friends cannot outlive the budget they were given. One nanoTime() per checkpoint (measured at ~0.01 µs) buys deadline enforcement that no longer depends on a timer thread being punctual.
A8

There is no way to run one scoped task

missing primitive code reading §二 · Batch = 同构映射, Group = 异构协调

Par exposes exactly one work-submitting method: map. The abstraction boundary reads "batch = homogeneous fan-out, group = heterogeneous coordination" — and leaves the unary case, the smallest unit of the thing this library is about, with no entry point at all.

Par.java — public methods: globalPar(), name(), map(List, Function, BatchOptions)

To run a single task with a deadline, TTL propagation, and structured cancellation, a user must write par.map(singletonList(x), f, opts).results().get(0) or stand up a one-member TaskGroup with a TaskKey. Both are ceremony over an operation the kernel already supports directly: TaskSubmissions.prepare + submitScoped is exactly this, and TaskGroup calls it per member.

Direction Add Par.submit(Callable<T>, TaskOptions) returning TaskFuture<T>. By the evaluation checklist this is pure parameterisation of the existing kernel — no new concept, no second pipeline, cancellation and deadline inherited unchanged — and it removes the most common reason a user would reach for a raw ExecutorService and lose scoping entirely.
A9

installGlobal argues against itself, and cannot be undone

API code reading Axiom 3 · 宁可不提供某个能力

A process-wide AtomicReference, settable once, with no uninstall — and its own javadoc says applications should normally pass Par instances around instead of using it as a service locator.

GlobalPar.java:46,119 — INSTALLED.compareAndSet(null, globalPar), no clear path

The practical cost lands on tests and on any container that restarts a context in one JVM: the second install throws, and the first GlobalPar is pinned for the lifetime of the classloader even after close(). The repository's own test can only assert that a second install fails.

Direction Either delete it (Axiom 3's default, and the javadoc's own recommendation), or make it symmetric — have close() clear the installed reference so a lifecycle can legitimately repeat. Keeping a one-shot global that the docs advise against is the one option that serves nobody.
Tier B

Eight features that stop short of their own promise

Not bugs — declared capability that the implementation only partly delivers. These are the ones worth deciding on before 0.3 freezes the surface.

B1

TaskType is a three-valued enum with two distinguishable values

half-builtcode reading

Every read in the library tests == CPU_BOUND. IO_BOUND and MIXED are therefore behaviourally identical, while MIXED's javadoc ("cache check first, then IO on miss") promises a distinction that does not exist.

grep TaskType. in src/main → 6 sites, all CPU_BOUND comparisons
Direction Either give MIXED real semantics (it plausibly means "may enqueue, never run inline") or collapse the enum to the boolean it is. A public enum whose values are indistinguishable teaches users a distinction the runtime will not honour.
B2

BlockingRisk declares four states and can only ever produce two

half-builtcode reading

VIRTUAL_THREAD_PER_TASK and UNBOUNDED are never assigned. detectRisk maps ThreadPoolExecutor → BOUNDED_PLATFORM_POOL and everything else to UNKNOWN, ignoring the two facts that actually determine nesting risk: queue boundedness and maximum pool size.

BlockingRisk.java:4-8 (4 constants) · ExecutorRuntime.java:70-75 (2 outcomes)
Direction Classify from the pool's real shape — bounded queue plus fixed maximum is the deadlock-prone case; an unbounded queue is a different risk (memory, not deadlock) and deserves its declared constant. A `ForkJoinPool` should not silently read as unknown. Combined with A4, this is the difference between a deadlock detector that works on real applications and one that works on the pools the tests happen to build.
B3

Batch elements cannot throw checked exceptions; group members can

inconsistencycode reading

Par.map takes Function<? super T, ? extends R>, so every element body that calls IO must wrap its checked exceptions by hand. TaskGroupDefinition.task takes Callable<T> and does not. Axiom 4 says to follow JDK idiom, and the JDK idiom for "work that may throw" is Callable.

Par.java:93 Function vs TaskGroupDefinition.Builder Callable
Direction Accept a throwing function in the batch path (a package-level ThrowingFunction<T,R>, or overload with Function<T, Callable<R>>). Under the 0.x breaking-change allowance this is cheap now and expensive later.
B4

The 90% batch case needs three steps and a Guava import

ergonomicscode reading

"Run these, give me the results, fail if any failed" is map(...) → .results() → Futures.allAsList(...) → .get(). And the input must be a List — no Collection, Iterable, or Stream, though nothing in the kernel needs indexed access beyond list.get(index) during preparation.

Direction One convenience on TaskBatchResult (values() / valuesOrThrow()) covers the common path without a new concept, and widening the input to Collection costs one ArrayList copy on entry. Pairs naturally with A2's terminal accessor — same idea, both entry points.
B5

Batches report; groups do not

asymmetrycode reading

TaskBatchResult has report() and reportString(); TaskGroupResult — which holds strictly richer data, per-member snapshots with timings — has neither. Meanwhile BatchReport.stateCounts() is annotated @Nullable for a null that report() never produces, forcing a dead null-check on every caller, and BatchReport's constructor is public although users never build one.

TaskBatchResult.java:96-131 · BatchReport.stateCounts() @Nullable · TaskGroupResult.java (no report)
Direction Drop the impossible null and the public constructor, then give the group the same one-line summary. Two symmetric results should answer the same question the same way.
B6

GlobalPar.close() cannot be joined

lifecyclecode reading

close() flips a flag and shuts the framework services down once admissions and batches drain — but exposes no way to wait for that. There is no awaitTermination, and activeBatches is private, so an application shutdown hook has no join point and no observability.

GlobalPar.java:235-241 close() · activeAdmissions/activeBatches private

The internal threads are daemons, so JVM exit is safe. A container redeploy is not: in-flight timeout actions keep the old classloader alive with nobody able to wait for them.

Direction awaitQuiescence(Duration) returning whether it drained, plus an in-flight count for metrics. This is also what A1 needs if close() becomes joining — same plumbing, two callers.
B7

Checkpoints is 30-plus methods of one pattern, with uneven coverage

surfacecode reading

541 lines in which nearly every method is: check the token, call the JDK operation, translate InterruptedException. The coverage that resulted is uneven — CountDownLatch has an untimed checkAwait but Semaphore has only timed tryAcquire; there is no Lock.lock() adapter; and no method derives its wait from the deadline the token already holds (see A7).

Direction Keep the handful of genuinely common wrappers as sugar, but express them over one parameterised primitive (Checkpoints.interruptible(op)) so coverage stops depending on which methods someone got around to writing. This is the "parameterise, don't multiply concepts" checklist item applied to the library's largest public class.
B8

18% of main is a queue library the toolkit never uses

scopecode reading

DrainingBlockingQueue is 1 642 lines — the largest file in the project by 2.6× — is public API, has its own contract document and 1 448 lines of tests, and is referenced from src/main only by its own package javadoc. Its sibling VariableLinkedBlockingQueue is reached only through SmartBlockingQueue, and carries both P1 defects from the September 10 report.

ComponentLOCUsed by the kernel?
queue/DrainingBlockingQueue1 642No — package javadoc only
queue/VariableLinkedBlockingQueue516Indirectly, via SmartBlockingQueue
SmartBlockingQueue86Never constructed by the library (A3)

CLAUDE.md calls this package "independent general-purpose queue implementations", so the coupling is intentional. The question is whether a structured-concurrency toolkit should ship it: it doubles the review surface, and its defects are now this artifact's defects.

Direction Split it into a sibling artifact (…-queues) that the core depends on, or drop it from the public surface and keep only what SmartBlockingQueue needs. 0.x is the cheapest moment this decision will ever have.

Recommendation

Suggested sequence

Ordered by "decision needed before code" first, then by payoff per unit of risk. The five defects from the September 10 report stay ahead of all of this.

  1. Decide A1 before anything else. Whether close() joins determines what the library is, and B6's awaitQuiescence is its implementation. Every other API choice reads differently depending on this answer.
  2. Then A3 + A4 together. Both are "a feature silently does nothing depending on how the user built their pool", both live in register/ExecutorRuntime, and B2's risk classification is the same edit. One change, three findings.
  3. A5 and A6 next — small, local, high blast radius. Two type-check expressions and one checkpoint signature. Both convert a documented guarantee from nominal to real, and A5 becomes moot if the v0.3 TaskKey removal lands, so sequence it against that proposal.
  4. A2 + B4 + B5 as one ergonomics pass. Terminal accessors and a symmetric report across both entry points — no new concepts, and it closes the "forgot to check" hole on the paths users actually write.
  5. A7 with defect #4. The clock-reading checkpoint is the backstop that makes that fix robust rather than merely correct-when-the-timer-is-punctual. Same area, one test matrix.
  6. A8 once A1 is settled. A unary submit inherits whatever close() semantics you chose, so build it after, not before.
  7. Tier C opportunistically, except C1/C2/C11, which change the public surface and therefore belong in the same release as the other API decisions. C13 today — it costs two lines.
  8. B8 is a product decision, not a refactor. Worth an ADR either way: 18% of the codebase and two P1 defects currently ride along on a promise the toolkit does not make.
Negative results

Checked and found sound

Where I went looking and found nothing worth reporting — as useful as the findings, since it marks where not to spend the next review.

  • Java 8 compatibility holds. maven-compiler-plugin uses <release>8</release>, which enforces the JDK 8 API surface, and Guava 33.6.0-jre still ships class-file major version 52. The stated floor is real, not aspirational.
  • ExecutionPhaseHintFuture's phase machine is airtight. The run()/afterDone() monitor discipline genuinely closes the lost-cancel-signal window, and the comments explaining why are accurate.
  • Admission counting is correct. enterAdmission's retry loop terminates in at most two iterations, and the activeAdmissions/activeBatches handshake into shutdownServicesWhenAdmissionsComplete has no path that leaks a count.
  • Token attribution is genuinely race-free by construction. Committing state before cancelling futures, then reading state post hoc — plus originState()'s parent walk — is the right design, and TokenOutcomes being the single mapping table is what makes it reviewable. This is the strongest part of the codebase.
  • TTL and context restore are balanced on every path. Normal, exceptional, cancelled, rejected, and inline all restore, including the deliberate restore(null) around listener notification so listeners cannot inherit a current-task identity.
  • The purge scheduler thread is lazy — my hypothesis that a disabled purge policy still costs a thread was wrong, and its probe said so.
