# 复杂需求不要一次写完：我用 Codex 小步重构一个生命周期 BlockingQueue

给 `BlockingQueue` 增加生命周期，最初听起来并不是一个很大的需求：队列关闭后，不再接受新元素，并且释放正在等待的线程。

但真正开始实现后，问题很快变得复杂。关闭时，阻塞在 `put` 和 `take` 上的线程分别应该得到什么结果？已经进入队列、还没有被消费的元素属于谁？关闭方法返回时，队列是否已经真正终止？`iterator`、`drainTo`、批量删除和反向视图又该遵守什么规则？项目还要保持 Java 8 字节码，同时希望在新 JDK 上兼容 `SequencedCollection`。

可以把这些问题放进一个最小场景：队列已经满了，生产者 P 阻塞在 `put(x)`；消费者 C 正在取元素；线程 S 此时发起 shutdown。接下来必须回答三件事：P 最终得到异常，还是可以认为 `x` 已经入队？关闭前已经入队但尚未消费的元素归谁？shutdown 返回时，P 和 C 是否都已经退出？

如果一开始就尝试回答所有问题，很容易得到一个看起来完整、实际上混入了大量未经验证假设的设计。

这次我没有先写一份终极规格，而是和 Codex 进行多轮小步迭代。每一轮只处理一类不确定性：先理解现状，再替换协调机制，然后补生命周期测试，继续追问关闭语义，最后回到标准库逐项校准集合契约。

回头看，这个过程很像一次持续重构。变化的不只是代码，还有我们对需求本身的理解。真正被逐步完成的不是一组方法，而是上面三个问题背后的并发契约。

## 一、先盘点已有探索，再从头定义问题

我的第一个提示词很简单：

> 总结一下当前 BlockingQueue 的实现和原理。

这一步没有产生代码，却很重要。项目原本有用于生产调度的队列，但生命周期支持还不是一项成熟能力。在正式设计新的生命周期队列之前，我只做过两个方向的小型探索：一个队列自己持有节点和同步状态，另一个通过包装任意 `BlockingQueue`，尝试在外部增加关闭能力。

这两个实现不是一套已经确定的架构，也不是可以直接投入使用的候选方案。它们更像是验证想法的原型，分别暴露了两条路线的边界：包装器无法控制被包装队列，也就是 delegate 的锁和等待条件，只能登记阻塞调用，并通过线程中断尝试唤醒它们；自有队列掌握节点、锁和等待条件，因此可以把生命周期直接写进并发协议。

所以，这一阶段并不是在几个成熟实现中做选择，而是借助已有探索，从头回答新设计最基本的问题：生命周期由谁拥有，关闭需要保证什么，哪些机制值得保留。只有先区分“如何中断一个未知队列”和“如何关闭一个自有队列”，后面的设计才不会建立在错误前提上。

这也形成了之后一直有效的工作方式：先让 Codex 解释现有结构和责任边界，再决定在哪一层修改。对于复杂需求，理解错误的代价通常比编码错误更高。

## 二、先做局部重构，再观察新的问题

第一轮实际修改仍然很克制：

> LifecycleQueue 改成使用 Guava Monitor 替换现有的 ReentrantLock。

这一轮的目标不是重新设计队列，而是在尽量保持公开行为的前提下，替换内部协调机制。队列继续使用两个独立的协调器：一个控制生产者进度，一个控制消费者进度。正常的容量和非空条件之外，Guard 还要包含生命周期关闭条件。

这样一来，等待线程不只会在“队列有空间”或“队列有元素”时被释放，也会在队列开始关闭时被释放。被唤醒后，它仍然必须在持有对应 Monitor 的情况下重新检查生命周期，确认可以提交后才真正修改队列。

回到开头的场景，Guard 解决的是“shutdown 后如何让 P 和 C 不再无限等待”。但被唤醒不等于操作成功：P 必须重新检查队列是否仍然接纳元素，只有检查与入队提交都成功，`x` 才真正属于队列。

这次重构看似只是锁 API 的变化，实际暴露了许多必须回答的问题：

- 两个 Monitor 同时获取时，锁顺序是否固定？
- 超时操作是否保留了原来的时间预算？
- 多个等待者能否在关闭后全部退出？
- `remove`、`clear` 和 `drainTo` 是否会正确推动另一侧继续执行？
- 外部中断与生命周期关闭能否保持不同的结果？

这些问题没有必要在第一次提示词里全部预见。小步重构的价值之一，就是先让一个局部变化落地，再根据它暴露出来的风险决定下一步，而不是在没有证据时扩大设计。

## 三、用追问和测试把“关闭”变成契约

锁替换完成后，我没有马上继续增加功能，而是换了一个角度：

> 生命周期相关配置有哪些测试，缺的话补全，哪些核心约束需要测试？

这让讨论从“实现是否能工作”转向“哪些行为必须持续成立”。测试开始覆盖状态迁移、阻塞方法的启动行为、重复关闭、多生产者和多消费者的释放、超时清理，以及外部中断和关闭异常之间的区别。

其中一类测试可以概括为：

```text
Given：生产者已经进入等待，待提交元素仍在生产者手中
When：另一个线程发布关闭
Then：所有等待中的生产者都得到 QueueShutdownException
And：这些未提交元素不会出现在终止后的恢复列表中
```

它固定了两个过去混在一起的问题：线程是否被释放，以及操作是否已经提交。仅仅看到线程返回还不够；测试还必须证明关闭之后没有发生一次迟到的入队。

紧接着，我又追问：

> 有没有可能触发关闭，但是不能真正关闭，就像关闭线程池需要线程实现处理中断，否则会持续等待？

这一步让“关闭”被拆成了几个不同事件：关闭请求已经发布，等待条件已经改变，阻塞调用已经返回，以及服务已经进入终止状态。它们并不必然发生在同一个时刻。

审查还发现了一个更隐蔽的问题：即使 Guard 设计正确，只要在 Monitor 内调用外部代码，关闭仍然可能卡住。例如，`drainTo` 的目标集合可以在 `add` 中永久阻塞，`remove(Object)` 触发的 `equals` 也可能执行未知逻辑。只要这些回调持有队列 Monitor，`stopAsync()` 就可能连关闭状态都无法及时发布。

因此后续实现把目标集合调用、相等判断、谓词和 Service listener 等用户代码移到 Monitor 之外。需要修改队列的路径要么在重新进入受保护区域后再次确认状态再提交，要么先完成队列内部的摘取，再调用外部代码。这里得到的教训是，复杂并发组件的终止能力不只由等待和唤醒决定，还取决于临界区里是否存在不可控代码。

同一阶段，我还问过 `LongAdder` 是否比 `AtomicInteger` 更适合写多读少的计数。最后保留 `AtomicInteger`，原因不是性能测试不够，而是这些计数参与容量判断、Guard 条件和精确的终止判定。它们是正确性状态，不是近似指标。

测试和追问在这里发挥了相同作用：它们都在迫使一个模糊概念变成可以观察、可以反驳的契约。

## 四、新设计的重点从“释放线程”转向“元素所有权”

当等待者可以被可靠释放后，新的问题出现了：关闭时，队列中还没有被消费的元素怎么办？

这也推动了架构上的进一步选择。包装任意 delegate 的方案可以尽力唤醒未知队列中的阻塞调用，却无法定义节点何时真正进入队列，更难给出精确的元素所有权。因此后续设计转向自有节点和同步状态的 `LifecycleQueueV2`。从这一节开始，讨论的已经不只是如何释放线程，而是如何让关闭成为队列自身协议中的一个原子事件。

我希望服务终止后可以取得这些元素，于是设计中加入了 `remainingList()`。这并不是简单地在关闭时调用一次 `drainTo`，因为它涉及一个更基础的问题：在关闭和入队并发发生时，元素到底属于队列还是生产者？

最终设计用关闭线性化点回答这个问题：

- 在线性化点之前已经链接到队列的元素，属于关闭后的恢复列表；
- 仍然保存在阻塞生产者局部变量中、尚未链接的元素，从未被队列接纳，仍属于生产者；
- 已经被消费者取出的元素不再属于队列；
- poison 只是结束信号，也不能混入恢复列表。

为了让关闭路径保持可控，shutdown 在同时持有两个 Monitor 时关闭 admission，也就是停止接纳新的阻塞操作，并以 O(1) 方式摘下整条节点链，再安装一个新的空哨兵。这样，关闭临界区的耗时不随剩余元素数量增长。旧链只在服务进入 `TERMINATED` 后、`remainingList()` 第一次被访问时才遍历，并物化成一个共享的 `CopyOnWriteArrayList`，让恢复代码可以并发读取或修改它，而不再影响队列。

生命周期模型也在这一阶段得到简化。Guava `Service` 有 `NEW`、`STARTING`、`RUNNING`、`STOPPING` 和 `TERMINATED` 等状态，但这些是集成接口的状态。对队列自身的正确性来说，更直接的模型是：

```text
OPEN -> CLOSING -> CLOSED
```

框架状态可以映射到它，不能反过来替代领域状态。

这两个状态模型仍然承担不同职责：`CLOSING` 表示队列已经停止接纳并释放等待者，`CLOSED` 表示此前获准进入的阻塞调用都已经退出；只有对应的 Guava Service 到达 `TERMINATED` 后，`remainingList()` 才允许访问。这样，“发起关闭”“队列不再接纳操作”和“恢复列表已经稳定”就不会被压缩成同一个含糊的“关闭后”。

这一轮让我意识到，复杂需求经常不是在编码前就完整存在。只有先实现“释放等待者”，才能看见“恢复元素”；只有讨论恢复元素，才会被迫定义 admission、线性化点和所有权。

## 五、回到标准库，撤销没有依据的约束

新的生命周期队列已经具备基本能力后，我开始感到另一个问题：实现与 `LinkedBlockingQueue` 的普通集合语义差别太大。

于是提示词变成了：

> 这里的实现应该参考标准库中 LinkedBlockingQueue 和契约。实际上大部分内容应该是语义一致的。

这带来了一次很重要的方向调整。生命周期扩展确实需要改变关闭后的行为，但它不意味着 iterator、bulk operation 或普通集合视图也应该随意发明新语义。

最典型的是 iterator。早期实现采用了稳定快照，并且交接文档一度把它写成需要保留的约束。后来我继续追问：

> iterator 的实现是否使用 JDK 中的实现更好？

在确认稳定快照并非生命周期所必需后，我明确要求撤销它：

> 不需要创建稳定快照。这个约束是你提出的，不是我强制要求的。目前的要求是尽量和标准库的实现一致。

最终 iterator 改为参考 Java 8 `LinkedBlockingQueue.Itr`：弱一致而非快照，缓存下一个元素，识别 dequeue 产生的 self-link，跳过已清除节点，并按节点身份执行 `remove()`。

这次修正比 iterator 本身更值得记录。和 Codex 合作时，模型会为了让设计闭合而主动补充约束，其中一些很有价值，另一些只是当时看起来合理。如果不持续追问约束的来源，这些临时选择很容易进入文档，随后被误认为不可修改的需求。

因此我开始用三个问题审查每个差异：

1. 这是用户目标，还是模型提出的实现选择？
2. 它是否由生命周期语义直接要求？
3. 如果撤销它，是否可以回到更熟悉的 JDK 契约？

最终形成的原则很简单：生命周期没有要求改变的地方，尽量遵循标准库。

## 六、既然返回 List，就兑现 List 的契约

同样的原则也被用于反向视图和 `SequencedCollection`。这里需要先区分需求来源：反向视图是已经明确要公开的能力，不是生命周期自然推导出来的要求；真正需要继续判断的是，既然公开了它，应该兑现到什么程度。

项目仍然需要生成 Java 8 字节码，因此生产类不能直接在签名中引用 Java 21 才出现的 `SequencedCollection`，除非提高发布基线或采用 multi-release JAR。最终设计提供同名的首尾操作，并让 `reversed()` 返回一个 `List`。在 Java 21 及以上版本中，这个返回的 `List` 本身也是 `SequencedCollection`；队列对象本身并没有因此实现 Java 21 的新接口。

开始时，反向视图只实现了有限能力。继续审查后，我提出：既然方法声明返回 `List`，就不应只实现几个方便的方法，而应遵守可变 `List` 已经向调用者作出的承诺。

这意味着 `reversed()` 不能只是一个方便读取的包装器，而要成为真正写穿原队列的可变 `List`：支持任意位置的 `get`、`set`、`add`、`addAll` 和 `remove`，遵守 `ListIterator` 的游标和“上一次返回元素”状态机。双重 `reversed()` 也必须继续写穿原队列。

这里还有一个容易混淆的区别。队列自身的正向 iterator 继续遵守 `LinkedBlockingQueue` 的弱一致语义；反向视图返回的是可变 `List`，它的 `ListIterator` 在队列发生外部结构修改时选择 fail-fast。两者服务于不同的公开契约，并不是同一个 iterator 前后采用了两套规则。

这里的取舍是：生命周期仍然是主要目标，但一旦主动公开了一个标准集合形态，就不应该只实现最顺手的几个方法。否则使用者看到的是熟悉的接口，得到的却是一组需要重新学习的局部规则。反过来，如果没有明确的反向视图需求，更克制的选择仍然是不公开这个接口，而不是为了“兼容”主动扩大范围。

## 七、关闭策略的变化不是反复，而是分类逐渐清晰

关闭后的行为经历过几次调整。早期我希望构造器可以选择抛异常或 `NOOP`，给调用者更多自由。随后在契约审查中发现，`NOOP` 会让某些操作在关闭后看起来成功，甚至可能让本来不应返回 `null` 的消费者方法返回 `null`。

于是实现一度收紧为关闭后统一抛出 `QueueShutdownException`。但进一步考虑真实消费循环后，最终又增加了 poison object 形式。

poison 解决的是消费者如何显式结束循环。例如多个消费者都可以在 `take()` 返回同一个保留对象时退出，而不需要真的向队列插入与消费者数量相同的结束元素。调用者必须按对象身份比较它，因为相等但不是同一个实例的元素仍然可以作为普通数据进入队列。

最后的策略不是回到最初的宽松设计，而是形成了更清楚的分类：

- 所有生产、bulk、iterator 和反向视图修改在关闭后都抛异常，不能静默成功；
- 元素移除型消费者可以由构造器选择抛异常，或者返回同一个 poison object；
- poison 是虚拟结束信号，不进入节点链、不占容量、不出现在 iterator 中，也不进入 `remainingList()`；
- poison 按身份保留，不能被当作普通元素入队。

同时，构造器补齐了标准集合常见的形式，可以从 `Collection<? extends E>` 按 encounter order 初始化，也可以组合容量、名称、关闭策略和 poison，并一次性验证 null、容量和保留对象冲突。

从 `NOOP` 到异常，再到 `THROW/POISON`，表面看是需求反复，实际上稳定原则一直在变得更明确：关闭后修改不能伪装成成功，而消费者结束信号可以有两种显式表达。

## 八、我最终形成的 Codex 小步迭代方法

这次 BlockingQueue 的最终设计并不是第一轮提示词规划出来的。它是在一次次解释、修改、测试、质疑和回退中逐渐形成的。

整个过程可以归纳为一个循环：

```text
解释当前实现
    -> 只修改一个维度
    -> 追问失败模式
    -> 用测试固定行为
    -> 对照标准实现
    -> 审查约束来源
    -> 同步实现与文档
    -> 进入下一轮
```

其中几类提示词尤其有效。

第一类是建立上下文：

> 总结当前实现和原理。

第二类是把隐含要求变成可验证行为：

> 哪些核心约束还没有测试？

第三类是寻找终止和并发边界：

> 有没有可能已经触发关闭，但不能真正关闭？

第四类是控制自定义设计的扩张：

> 与标准库的契约差异中，哪些是生命周期真正需要的？

第五类是审查人机协作中最容易被忽略的问题：

> 这个约束是我的要求，还是你自己提出的设计？

Codex 很适合快速展开实现空间、列出边界条件、补充测试和持续重构，但它也会自然地尝试补全设计。人的职责不是逐行指导它写代码，而是判断哪些约束代表真正目标，哪些只是工程手段，哪些应该在新证据出现后被撤销。

设计文档在这个过程中也不能只记录“当前代码怎么做”。最终文档需要明确区分用户目标、项目发布边界和实现选择。只有这样，双 Monitor、O(1) 摘链或延迟物化之类的工程方案才可以继续演进，而不会被误当成永久需求。

小步迭代因此不只是把大任务拆成许多小任务。更重要的是，让每一轮只承担一组可以解释、验证和撤销的约束。每一轮也不以“增加了多少代码”为完成标志，而以“消除了一类不确定性，并留下可执行的契约”为完成标志。

对于这类要求很高的并发组件，这比一开始就追求一个看似完整的最终设计更可靠。第一版不需要回答所有问题，它只需要足够清楚，让下一轮知道应该继续问什么。
