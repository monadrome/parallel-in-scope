# Purge 核心需求与第一性原理（讨论稿）

> 状态：核心需求与首版实现已完成，仍需性能数据校准；本文不是稳定 API 文档。
>
> 本文先回答“为什么需要 purge、要解决什么、成功标准是什么”，再讨论候选机制。

## 1. 问题定义

线程池工作队列可能继续持有已经取消、尚未开始执行的任务。只要队列节点仍然存在，任务对象及其捕获的业务对象就不能回收，对应队列容量也不能重新用于有效任务。

这个问题在以下条件同时出现时最明显：

1. 工作线程长时间被占用，队列消费速度很低或为零；
2. 大量已提交任务因超时、失败即止或父任务取消而被取消；
3. 取消只改变 Future 状态，没有立即从工作队列移除对应节点；
4. 队列中仍有大量取消节点，导致引用滞留或有效容量下降。

这里更准确的名称是“取消任务的队列滞留”，不应笼统称为内存泄漏。只要 worker 最终继续消费，滞留可能自行消失；当 worker 永久阻塞时，滞留时间才可能变成无限。

## 2. Purge 能解决什么

Purge 的唯一职责是：

> 以可接受的维护成本，从工作队列中移除已经取消、尚未开始执行的任务节点。

它产生两类直接收益：

- 释放队列对任务及其捕获对象的强引用；
- 释放有界队列槽位，使后续有效任务可以入队。

它不能解决：

- 已经开始运行且永远不返回的任务；
- 忽略中断的任务；
- 不可中断 I/O；
- 线程池容量规划错误；
- 业务任务没有协作式取消检查。

永久运行任务需要通过协作式取消、可中断 I/O、超时、线程池隔离和容量限制治理。Purge 不能成为这些问题的兜底机制。

## 3. 第一性原理约束

### 3.1 正确性优先于回收速度

清理操作只能移除已确认取消的队列节点，不能移除仍可能执行的正常任务。

取消原因不能作为队列归属证据。`CancellationToken`、`FatCancellationException` 和 `LeanCancellationException` 只能说明取消或异常传播发生过，不能证明对应任务仍在某个工作队列中。运行中任务、其他线程失败触发的级联取消也可能产生同类信号。

因此，清理候选必须来自“实际提交到该队列的任务对象”的生命周期，而不是批次报告或异常类型。

### 3.2 清理收益必须大于扫描成本

扫描队列本身会消耗 CPU，并可能竞争队列锁。每次取消都扫描，等价于把取消突发放大为维护突发。

清理决策至少需要同时考虑：

- **容量压力**：队列是否已经接近其可用容量上限；
- **垃圾比例**：一次扫描预计能回收多少取消节点。

只有队列有压力且预期回收比例足够高时，扫描才值得执行。

### 3.3 信号必须廉价，重活必须合并

取消路径属于业务关键路径。它最多执行常量时间的状态更新和调度请求，不应遍历队列或等待维护锁。

同一执行器上的一批并发取消应合并为一次维护，而不是一项取消对应一次 purge。任意时刻每个队列最多有一个已调度或正在执行的清理任务。

### 3.4 所有统计都是并发近似值

计算阈值时，worker 可能出队，新任务可能入队，队列容量也可能动态调整。因此队列长度、容量和候选取消数不可能构成事务一致快照。

这不是需要消除的竞态。阈值只用于判断“现在是否大概率值得扫描”，不能作为精确账本或正确性依据。清理操作本身仍必须逐项确认取消状态。

### 3.5 状态按实际队列隔离

容量、队列长度、取消候选和清理中的状态都属于具体工作队列。不同执行器之间不能共享统计，否则一个池的取消会触发另一个池的扫描。

Future 到执行器的关联只是为了把取消信号路由到保存该任务的队列。它不应演变为全局 Future 注册表，也不应使已完成或长时间运行的 Future 永久持有整个执行器。

### 3.6 不支持的队列必须安全降级

当前讨论只覆盖 `SmartBlockingQueue`。其他队列不应通过反射、名称解析或不可靠假设接入；应明确不执行自动清理。

## 4. 触发模型

先定义讨论用变量：

- `Q`：决策时观察到的队列节点数；
- `K`：队列当前配置容量；
- `G`：自上次清理以来观察到的“可能仍在队列中的已取消任务”数量；
- `P = Q / K`：容量压力；
- `R = min(G, Q) / K`：估算垃圾占队列总容量的比例。

`G` 不是已取消队列节点的精确数量。任务可能已被 worker 取走但尚未进入用户代码，也可能在信号处理前被其他并发操作移除。

### 4.1 基本触发规则

一次自动清理应同时满足：

1. 发生过实际已提交任务的排队期取消，`G > 0`；
2. 当前没有该队列的清理任务处于已调度或执行状态；
3. `P >= capacityPressureThreshold`；
4. `R >= cancelledRatioThreshold`。

两个阈值采用 **AND** 关系：

- 只有容量压力，没有足够垃圾时，扫描收益太低；
- 只有垃圾比例，没有容量压力时，立即回收的业务价值较低；
- 两者都高时，清理最可能改善有效容量并释放明显数量的引用。

当前建议默认值仍可作为讨论起点：

- `capacityPressureThreshold = 0.80`；
- `cancelledRatioThreshold = 0.05`。

这些值不是正确性常量，需要通过真实队列规模、取消突发和扫描耗时校准，并允许运行时配置。

### 4.2 合并规则

阈值首次满足时提交一个固定延迟 50ms 的维护任务，把同一突发中的信号合并。提交成功后，直到该任务结束，取消 callback 只递增一个单调序列号并返回；它不读取队列、不计算阈值、不记录日志，也不重新提交任务。后续信号由维护任务结束时的握手进入下一轮，因此持续取消不会把 50ms 窗口不断向后滑动。

每个执行器使用 `IDLE -> SUBMITTED -> RUNNING -> IDLE` 状态机，同一时刻最多一个已提交或正在执行的清理任务。维护任务在执行前重新读取近似值；purge 扫描开始前记录 `issuedSequence`，扫描期间到达的新信号不会被本轮成功结算。

固定周期扫描不符合需求：没有取消时它做无效工作，取消突发时又可能响应过慢。

### 4.3 阈值未满足时的状态

未满足阈值不代表丢弃 `G`。后续取消或容量增长可能使累计需求达到阈值。

但 `G` 也不能无限代表历史垃圾：队列变空时应归零；成功清理后应结算本轮候选；worker 的自然消费会使它逐渐高估，因此触发前必须用 `min(G, Q)` 限幅，再除以容量 `K`。

低压力下长期累计的历史 `G` 不应永久参与后续判断，否则队列重新装入正常任务后可能被旧数据误触发。

采用简单的**惰性过期**，不增加周期任务：

1. 每个队列用原子标记记录 reset generation、已观察序列和时间；
2. 下一次处于 `IDLE` 的取消信号到来时原子替换标记并计算时间间隔；
3. 如果间隔超过内部固定的过期窗口，只把标记中明确观察到的旧序列结算，不把并发首批新信号误清掉；
4. 队列为空、禁用重置或 purge 成功后，通过 `settledThrough` 高水位结算，不把计数器直接设回零。

该规则是 `O(1)`，只在已有取消事件上执行。它不是连续、精确的数学衰减，但足以阻止很久以前的取消记录污染新一轮队列压力。过期窗口先保持内部常量，不增加第三个公共调参项；并发边界允许少量高估或低估，因为 `G` 本来就是启发式数据。

## 5. 扫描成本是核心设计输入

不能只讨论“何时调用”，还要讨论“一次清理到底多贵”。

JDK `ThreadPoolExecutor.purge()` 通常遍历工作队列，并通过迭代器删除已取消 Future。当前 `VariableLinkedBlockingQueue` 的 `Iterator.remove()` 会从队首重新查找目标节点，并在删除期间获取完整队列锁。

若队列长度为 `Q`、取消节点数为 `D`，当前组合最坏可能接近：

```text
遍历成本 O(Q) + 删除查找成本 O(Q × D)
```

这意味着垃圾比例越高，调用 `ThreadPoolExecutor.purge()` 的单次成本反而可能越高。阈值只能降低调用频率，不能修复单次扫描复杂度。

已确认的执行边界是：**清理必须调用 `ThreadPoolExecutor.purge()`**。这里的 purge 不是泛指“实现相同清理效果”，不能用 `SmartBlockingQueue.removeCancelledTasks()` 之类的队列私有批量清理替代。

此前“是否接受为 SmartBlockingQueue 增加内部线性批量清理能力”的问题，实际是在询问是否允许绕过 `ThreadPoolExecutor.purge()`，直接让队列单次遍历删除取消节点。由于现在明确必须调用 `ThreadPoolExecutor.purge()`，该候选方案已经排除。

同样不采用取消时立即执行 `queue.remove(task)`：每次取消都可能扫描队列，取消突发会把成本放大到业务线程。

因此当前设计接受一个约束：两个阈值可以控制 purge 的触发频率和强度，但不能消除 `VariableLinkedBlockingQueue.Iterator.remove()` 带来的最坏复杂度。实施前需要用大队列测试记录 purge 耗时；若成本不可接受，只能在仍由 `ThreadPoolExecutor.purge()` 发起清理的前提下优化队列迭代器删除路径，不能替换 purge 调用。

## 6. 配置需求

需要一个总开关和两个强度参数：

| 参数 | 含义 | 建议初始默认值 |
|---|---|---:|
| `purgeEnabled` | 是否启用自动 purge | `false` |
| `capacityPressureThreshold` | `Q / K` 达到多少才认为队列有容量压力 | `0.80` |
| `cancelledRatioThreshold` | `min(G, Q) / K` 达到多少才认为扫描有足够收益 | `0.05` |

配置要求：

- 自动 purge 默认关闭，只有显式打开 `purgeEnabled` 才观察并触发清理；
- 两个比例范围必须明确并校验，拒绝 NaN 和无效比例；
- 开关和两个阈值都提供 getter/setter，运行时调整必须线程安全；
- 修改只影响之后的决策，不承诺重算历史状态；
- 关闭开关后不再累计新的 `G`，再次开启时从新的取消信号开始计算；
- 指标名称应表达业务含义，不暴露某个具体算法类名。

是否把静默窗口也开放配置，需要性能数据支持。没有真实需求前，应保持内部常量，避免形成不必要的公共 API。

### 6.1 两个阈值如何表达 purge 强度

两个阈值共同决定 purge 强度，不再增加“level”枚举或第三个强度参数：

| 配置方向 | 行为 |
|---|---|
| 两个阈值都降低 | 更激进，更早、更频繁地调用 purge |
| 两个阈值都提高 | 更保守，只在队列更满且预计垃圾更多时调用 purge |
| 只降低容量压力阈值 | 中低队列压力时也允许清理 |
| 只降低垃圾比例阈值 | 少量取消节点也可能触发清理 |

例如 `0.80 + 0.05` 只是默认起点，不代表唯一推荐组合。用户根据队列容量、任务对象大小和可接受的扫描开销选择不同强度。

### 6.2 “运行时可调”的含义

构建期配置意味着只能这样设置：

```java
ParConfig.builder()
        .purgeQueuePressureThreshold(0.80)
        .purgeCancelledTaskRatioThreshold(0.05)
        .build();
```

之后若要改变阈值，必须重建配置或重启服务。

运行时可调意味着服务运行期间可以调用 setter：

```java
config.setPurgeQueuePressureThreshold(0.60);
config.setPurgeCancelledTaskRatioThreshold(0.02);
```

新的取消信号立即使用新阈值，不中断任务，也不重建线程池。结合已经确认的 `AtomicDouble + getter/setter` 要求，本文采用运行时可调方案。总开关采用相同语义，默认关闭并允许运行时开启或关闭。

## 7. 可观测性需求

可观测性采用 trace 级别日志，不新增监听器或公共指标接口。

JUL 没有名为 TRACE 的级别，实现时使用最接近的 `Level.FINEST`，并在格式化字段前检查 `LOGGER.isLoggable(Level.FINEST)`。不为每个取消回调写日志，只在做阈值决策或执行 purge 时记录，避免取消突发产生同规模日志。

每条决策日志至少包含：

- 动作：`disabled`、`skip-pressure`、`skip-ratio`、`scheduled`、`purged` 或 `failed`；
- 队列当前长度与容量；
- 容量压力、垃圾估算比例及对应阈值；
- 本轮 `G`；
- purge 前后队列长度及耗时。

`ThreadPoolExecutor.purge()` 不返回实际移除数量，且扫描期间队列仍可并发变化，因此 `beforeSize - afterSize` 只能记录为近似变化，不能命名为精确删除数。purge 异常使用现有 warning 日志，不降为 trace。

## 8. 验收标准

### 8.1 行为正确性

- 只移除已取消且仍在 `SmartBlockingQueue` 中的任务；
- 不移除正常排队任务；
- 未提交的占位 Future 不产生清理需求；
- 已经开始运行的任务取消不计入队列垃圾；
- purge 后运行中的永久任务仍然运行，明确证明能力边界。

### 8.2 触发策略

- 容量压力低于阈值时不扫描；
- 垃圾比例低于阈值时不扫描；
- 两个阈值同时达到时最终执行一次清理；
- 总开关关闭时不触发 purge，且默认配置保持关闭；
- 运行时调整开关和阈值后，后续取消使用新配置；
- 一次取消突发只合并成一次在途清理；
- 清理期间的新取消不会丢失；
- 队列变空、purge 成功或取消信号长时间静默后，历史估算不会触发无效扫描。

### 8.3 性能与并发

- 取消回调不遍历队列、不阻塞等待清理完成；
- 队列入队、出队和容量调整并发发生时不破坏队列结构；
- 清理复杂度需要通过大队列基准验证，不能只用小规模单元测试推断；
- 清理不会形成固定周期后台负载；
- 维护线程失败或拒绝调度时，不影响 Future 的取消语义。
- 最终清理路径必须实际调用 `ThreadPoolExecutor.purge()`。
- 阈值决策和 purge 执行产生 `Level.FINEST` 日志，异常保留 warning 日志。

## 9. 已确认决策

1. 清理必须调用 `ThreadPoolExecutor.purge()`，不以队列私有清理方法替代。
2. 只支持 `SmartBlockingQueue`；普通队列安全降级为不自动清理。
3. 提供总开关，默认关闭，并允许运行时修改。
4. 使用容量压力和垃圾比例两个阈值表达不同 purge 强度，两个条件采用 AND。
5. 两个阈值通过原子 getter/setter 允许运行时修改。
6. `G` 使用无周期任务的惰性过期；队列为空或 purge 成功时清零。
7. 决策和执行记录 trace 日志，异常记录 warning，不新增监听器。
8. 不使用 BatchReport、CancellationToken 状态或 Fat/Lean 异常判断队列垃圾。

## 10. 首版实现选择与剩余验证

首版实现采用以下选择：

1. 公共开关命名为 `purgeEnabled`，通过 `isPurgeEnabled()` 和
   `setPurgeEnabled(boolean)` 运行时访问，底层使用 `AtomicBoolean`；
2. 惰性过期窗口固定为 1 分钟，不增加第三个公共调参项；
3. 取消突发使用固定 50ms 延迟合并；提交或执行期间 callback 只递增序列，维护结束后通过握手补交下一轮；
4. trace 日志使用执行器类名与 `System.identityHashCode` 形成的稳定对象标识，
   不重新引入 executor resolver；
5. purge 执行前重新读取两个阈值并使用 AND 判断，不允许后续轮次绕过阈值；失败需求保留并最多为同一序列安排一次 1 秒后重试。

仍需用大队列、高取消比例的基准数据判断 `ThreadPoolExecutor.purge()` 与当前
`VariableLinkedBlockingQueue.Iterator.remove()` 组合的实际延迟。该验证只影响性能优化，
不改变必须由 `ThreadPoolExecutor.purge()` 发起清理的边界。
