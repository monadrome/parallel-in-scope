为什么 ConcurrentHashMap 迁移不会重复访问同一个节点

——以及迁移过程中的锁是怎么用的，和迭代有没有关系

基于 JDK 8（Corretto 8.412）的 ConcurrentHashMap 源码与两个实测探针。 三个结论：① 迁移过程中迭代器不会重复访问同一个节点（遍历结构决定，与锁无关）； ② 迭代器全程无锁——不取锁、不被锁阻塞、也不阻塞任何写者； ③ 漏看是可能的，且只影响当趟遍历。
✓ 重复访问同一节点
不可能。每个 bin 恰好访问一次，且节点的入口唯一。
✓ 迭代器与锁
无直接关系。迭代全程无锁（volatile 读），锁是写给写者和迁移线程的。
⚠ 漏看
可能。插入到"已扫过 bin"的元素本趟不可见；下一趟可见。
🔒 锁的粒度
per-bin（synchronized (f)），写者与迁移共用；空 bin 用 CAS，迭代在锁外。

一、迭代器行走的三个事实

迭代器（Traverser）的行为由三个事实决定。理解了它们，"不会重复"就是顺理成章的结果。

事实 1：旧表的每个 bin 恰好被访问一次

事实 2：撞到 ForwardingNode 就"下降"，只扫 {i, i+n}

迁移进行时，transfer 每转发完一个 bin，就把旧表该 bin 替换成 ForwardingNode（转发节点，指向新表）。 迭代器撞上它时跳到新表，但不是从新表开头重新扫，而是只访问两个 bin：i 和 i + n（n = 旧表长度）—— 旧 bin i 迁移后正好分裂成这两个。扫完弹回旧表，从 i + baseSize 继续。

事实 3：节点迁移的终点，和下降覆盖的集合是同一个：{i, i+n}

transfer 把旧 bin i 的链表按 hash 的一位拆成两半，放回新表 bin i 和 i + n。 所以一个节点从旧 bin i 出发，只可能出现在新 bin i 或 i+n——没有第三条路。 图 2 里这一点已经画出来了：下降能扫到的集合，恰好就是节点能迁到的集合。

二、迁移与锁：谁在锁里，谁在外面

CHM 的并发控制分三层，锁只是其中一层，而且是每 bin 一把的小锁，不是全局锁：

操作同步机制说明
空 bin 插入（put / remove / compute…）casTabAt（CAS，无锁）源码注释原话："no lock when adding to empty bin"
非空 bin 的修改（put / remove / merge / compute）synchronized (f) + 双检锁的是该 bin 的头节点 f，再加 tabAt(tab, i) == f 双检

两个关键点：
· ② 迁移的是新建的节点（new Node / new TreeNode，只有链尾 lastRun 被复用）—— 旧表 bin 5 里的链从头到尾没被改过一根指针。所以锁外的迭代器读旧表时，看到的永远是完整旧链。
· ③ 是临界区最后一步，且是 volatile 写。迭代器要么在 ③ 之前读到完整旧链，要么在 ③ 之后读到 FWD 并下降—— 不存在"读到半截链"的中间态。这是无锁迭代安全性的来源。

锁外还有一层 CAS 协调：transferIndex 用 getAndAdd(-stride) 分片领活（多个线程各迁一段 bin）、 sizeCtl 记录扩容状态与参与线程数、baseCount / CounterCell 负责计数。这些是"调度"的锁， 和 bin 内容的互斥无关，也不影响迭代。

三、锁和迭代：直接无关，间接有关

直接答案：迭代和锁没有直接关系。迭代器全程无锁——不取锁、不等待锁、不被锁阻塞，也不阻塞任何写者或迁移线程。 锁是写给写者（put / remove / compute）和迁移线程（transfer）的互斥工具； 迭代器只做 volatile 读（tabAt + Node.next / Node.val）。

间接上，锁通过维护一个不变量，让无锁迭代变得安全。分三点说：

1. 可见性：锁内完成的写入，锁外的 volatile 读能安全看到。 迭代器不取锁，但它读的每个字段都是 volatile（bin 槽、Node.val、Node.next）。 迁移在锁内完成"写新表 + 放 FWD"，迭代器的 volatile 读要么命中 ③ 之前（完整旧链），要么命中 ③ 之后（FWD → 下降）， 不会撕裂。锁在这里的作用是保证写入顺序，而不是阻止迭代读取。

2. 不变量：锁维护"旧 bin 要么完整、要么 FWD"。 双检（①）防止重复转发；锁内三步（图 4）保证旧链不动、FWD 最后放。 迭代的正确性依赖这个不变量，但迭代本身不参与维护它——它只是"路过"。 helpTransfer（写者撞到 FWD 时帮忙迁移）只有写者会调用，迭代器从不帮忙，它撞到 FWD 只是借道下降。

3. 调度：锁只决定"bin 何时被转发"，不参与迭代的行走。 前面两刀切（下一节）的证明只用到了遍历结构（每个 bin 恰好一次 + 下降只扫 {i, i+n}）和不变量， 没有用到锁——即使迁移换一种完全无锁的实现，只要保持"旧 bin 要么完整要么 FWD"，"不重复"结论依然成立。 锁与不重复无关，只与"写写互斥"有关。

补充一点：remove() 摘链也会在 bin 锁内原地断开 pred.next，迭代器可能因此跳过一个节点 （删除路径的漏看来源之一）；但摘链只往前断开、不会造成回头，所以同样不会产生重复访问。

对照：为什么 CHM 敢让迭代无锁

实现迭代与锁并发修改时的行为
Hashtable / Collections.synchronizedMap方法级全局锁；迭代要么在锁内（外部同步），要么裸读裸读 + 并发写 → fail-fast 抛 ConcurrentModificationException
ConcurrentHashMap迭代完全无锁，per-bin 锁只属于写者和迁移不抛 CME，弱一致（可能漏看、不精确）；且迁移时也不会重复

原因：锁能买到的是"某个精确时刻的一致视图"，而 CHM 的弱一致性契约明确放弃了这个精确性—— 它用无锁迭代 + 弱一致换吞吐，代价是遍历结果不精确。既然不承诺精确，迭代就不需要锁。

四、两刀切：为什么不会重复

第一刀：bin 的访问次数 ≤ 1。（事实 1）旧表每个 bin 恰好被访问一次；"在 bin i 处下降"这件事，发生在迭代器到达 bin i 的那一刻，而 bin i 只会被到达一次，所以下降也至多发生一次。

第二刀：访问一个节点的唯一入口，是它所在的 bin。（事实 2 + 3）节点 X 在任意时刻只存在于一个 bin：迁移前在旧 bin i，迁移后在新 bin {i, i+n}。能碰到 X 的路径只有两条——直接扫到旧 bin i，或"在旧 bin i 处下降"扫到新 bin {i, i+n}——而这两条路径都要经过旧 bin i 本身，它只被访问一次。

组合起来：任何时刻，X 至多被访问一次。迭代器到达 bin 5 时只有两种可能，二者互斥：

图 5 · 只有两种时序，都不会重复

→

不存在"先扫旧表、之后又下降"的第三个分支：下降只发生在"到达 bin 时它已转发"这一种情况里。 一旦 bin 5 在到达前就被转发，X 就不会再被旧表扫到；一旦到达时还没转发，之后就没有任何路径再碰到 X。 分支 A / B 的分界由锁内放置 FWD 的时机决定（图 4 的 ③），但无论时机怎么变，结论都是 1 次。

// ① 可见性的基础：bin 槽、val、next 全是 volatile（迭代无锁的前提）
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    volatile V val;
    volatile Node<K,V> next;
}
static final <K,V> Node<K,V> tabAt(Node<K,V>[] tab, int i) {
    return (Node<K,V>)U.getObjectVolatile(tab, ((long)i << ASHIFT) + ABASE);
}

// ② putVal：一个循环里的三个分支，锁只出现在一个分支
Node<K,V> f = tabAt(tab, i);
if (f == null)
    casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)); // 空 bin：CAS，无锁
else if ((fh = f.hash) == MOVED)
    tab = helpTransfer(tab, f);          // bin 已转发：帮忙迁移，然后去新表重试
else {
    synchronized (f) {                   // 非空 bin：锁 bin 头节点（写者路径）
        if (tabAt(tab, i) == f) { ... }  // 双检
    }
}

// ③ transfer：同样的锁，同样的双检；临界区内三步 volatile 写（图 4）
synchronized (f) {
    if (tabAt(tab, i) == f) {
        // 拆链：全部新建节点（只有 lastRun 尾巴被复用），旧链一根指针都不动
        for (Node<K,V> p = f; p != lastRun; p = p.next)
            ln = new Node<K,V>(ph, pk, pv, ln);   // 或 hn
        setTabAt(nextTab, i, ln);       // ① 新表低半区
        setTabAt(nextTab, i + n, hn);   // ② 新表高半区
        setTabAt(tab, i, fwd);          // ③ 旧表 bin 原子替换为 ForwardingNode
        advance = true;
    }
}

// ④ Traverser.advance()：迭代器行走（事实 1 + 2，全程无锁）
if (stack != null)
    recoverState(n);
else if ((index = i + baseSize) >= n)
    index = ++baseIndex;                // 每个 bin 恰好访问一次
if (e instanceof ForwardingNode) {
    tab = ((ForwardingNode<K,V>)e).nextTable;   // 下降：只借道，不取锁、不帮忙迁移
    pushState(t, i, n);
    continue;
}
