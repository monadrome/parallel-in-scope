# Senate：多模型议会决策 + 廉价模型执行

> 状态：设计草案，尚未定稿。
>
> 一个跨项目通用工具的设计记录，借本仓库 design/ 暂存。它不是本库的 API 契约，
> 定稿后应迁至 `refs/` 或插件仓库。

## 〇、要解决的问题

代码库健康巡检的质量天花板，取决于**发现问题的那个模型有多强**；而修复的成本天花板，
取决于**动手的那个模型有多便宜**。这两件事目前被绑在同一个会话里。

Senate 把它们拆开：

- **决策**由多个顶级模型（各自的顶级 agent harness）独立巡检、交叉投票产生；
- **执行**由廉价模型按投票结果逐条落地；
- **正确性**不由投票提供，由视角分化、证据门槛、执行后验收三者提供。

参与席位（当前配置）：

| 席位 | Harness | 模型 | 通道 |
|---|---|---|---|
| A | Claude Code | `claude-opus-5` | 本机 firstParty |
| B | Codex | `gpt-6-astra` | 经 CCR 网关 `127.0.0.1:3456` |
| C | Kimi Code | `kimi-code/k3` | OAuth |

**席位身份是 `(harness, model)` 二元组，不是 CLI 名。** 实测不带 `--model` 的
`claude -p` 在本机跑的是 `deepseek-flash`——只写 CLI 名会让三个席位退化成同一批模型
自说自话。所有席位命令必须显式传模型。

## 一、调用关系：dispatch/signal，不是 call/return

这是本设计最核心的一条，决定了其余所有细节。

用 cmux 编排席位，意味着主席**不"调用"议员，而是"派遣"议员**。这不是 RPC，是 actor 式
的消息传递——三个后果，每个都必须在协议里显式兜住：

1. **信号不携带返回值。** `cmux wait-for` 只是一个命名同步令牌，它告诉你"这个席位举手
   了"，不告诉你它产出了什么。所以**产物必须落在文件系统里，且必须被独立校验**。
   信号 + 产物双确认，缺一不可。

2. **失败表现为超时，而不是异常。** 子进程模型下你拿到 exit code；这里你只等到一个
   沉默。所以缺席检测 = `wait-for` 超时，且**缺席要写进报告**，不能静默按在场人数算票。

3. **可以在轮询间隙干预。** 主席的等待是后台式的（见 Phase 2），不阻塞自己的会话；
   它能在两次轮询之间对干活的席位 `cmux send` 追加约束（"只看 `src/main/java`，
   别碰测试"）。这是轮询间隙的补充能力，不是随时随地的中断——真实的中途干预只发生
   在两次轮询之间。选 cmux 的核心理由是可观测性与可追问，干预能力只是附带收益。

### 相对 headless 子进程的取舍

| | headless（`claude -p` / `codex exec`） | cmux 会话 |
|---|---|---|
| 可见性 | 无，跑 20 分钟不知道钱花在哪 | 全程可旁观，`cmux tree` 直接标出状态 |
| 追问 | 一票投完即定局 | 可对证据不足的条目发起澄清轮 |
| harness 保真 | 沙箱常阉割工具集 | 跑原生 agent loop、原生工具与 MCP |
| 故障 | 对着超时的子进程猜 | 席位卡住一眼可见，可重派 |
| **硬预算闸门** | `--max-budget-usd`（仅 `--print`） | **没有等价物** |

最后一行是真实的代价：**换来可观测性和可追问，代价是失去金额硬闸门**。因此成本控制必须
由别的手段承担——收窄巡检范围、封顶条目数、显式超时、以及"人随时能叫停"。详见第八节。

## 二、角色与权力边界

```
┌─ 人类（cmux UI）───────────────────────────── 旁观 / 随时叫停 ─┐
│                                                                │
│  主席 Chair          席位 A/B/C（三个 workspace）               │
│  （本会话）          只读代码库                                  │
│  调度 / 归并 / 计票   只写 proposals/<seat>.json                 │
│  不投票 / 不写代码    完成后 cmux wait-for -S 举手               │
│                                                                │
│  执行者 Executor（第四个 workspace，廉价模型）                   │
│  唯一有写权限的角色                                             │
└────────────────────────────────────────────────────────────────┘
```

**三条边界，每条都有反例作为理由：**

1. **席位永不写工作区。** 三个 harness 都支持只读/计划模式，用它。能让议员改代码，
   它就会倾向于"帮你修了"而不是"报告问题"——验收机制里对 reviewer 的同一条约束在此
   同样成立，而且更致命：能改代码的议员让你无法区分"提案"和"既成事实"。

2. **主席不投票，只计票。** 主席下场投票，等于执行者给自己发许可证。

3. **执行者独立成席。** 而非主席兼任，有三个理由：主席的上下文是宝贵资源，不该被 15 条
   改动的细节挤爆；执行跑偏不污染议会记录；`cmux diff --last-turn` 能给执行者留下独立
   可审计的一轮。

## 三、一轮议会的阶段划分

```
Phase 0 建院      创建 run 目录、写 brief、拉起四个 workspace
Phase 1 提案      三席并行、互不可见、只读、lens 分化
Phase 2 收集      wait-for 屏障 → 超时判缺席 → 产物校验 → 一次补正
Phase 3 归并      按 anchor 预分组判重 → 匿名化 → 脚本真随机乱序 → 封顶截断 → 生成 ballot
Phase 4 投票      三席并行、互不可见、逐条投票、证据强制
Phase 5 计票      机械计票 + quorum 降级判定
Phase 6 执行      执行者逐条落地，每条跑 acceptance
Phase 7 闭院      保留席位 workspace 供审计，输出 report
```

**Phase 1 与 Phase 4 之间必须是硬屏障。** 提案阶段任何形式的互见都会污染后续投票。
这是整套机制里最容易因为图省事而破坏、也最不该破坏的一条。

### 各阶段的 cmux 原语映射

以下命令均以 `cmux --help` 输出为准；标注 ✓ 的为实测验证过。

**Phase 0 建院**

```bash
cmux new-workspace --name "senate/$RUN/seat-a" --cwd "$REPO" \
  --command "claude --model claude-opus-5 --permission-mode plan"
cmux new-workspace --name "senate/$RUN/seat-b" --cwd "$REPO" \
  --command "codex -m gpt-6-astra -s read-only"
cmux new-workspace --name "senate/$RUN/seat-c" --cwd "$REPO" \
  --command "kimi -m kimi-code/k3 --plan"
cmux new-workspace --name "senate/$RUN/executor" --cwd "$REPO"
cmux workspace status set lane        # 把席位归拢到状态栏
cmux set-progress 0.0 --label "senate: 提案中"
```

**建院第一步是自动探测席位可用性**：对每个席位 CLI 做一次最小调用（一行 ping prompt），
探测结果写进 `report.md`；探测失败的席位直接按缺席规划本轮，不等屏障超时才发现。

三个 harness 各自的只读入口：`--permission-mode plan`（Claude）、`-s read-only`（Codex）、
`--plan`（Kimi）。**这是协议要求，不是建议。**

**Phase 0.5 就绪门** ✓ 实测结论

`cmux send` 只输入文本、**不提交**，必须补发 `cmux send-key <ref> Enter`。席位 CLI
启动后还有交互式前置门，不能只等提示符：

- **Trust 门**：Kimi CLI 在任意新目录首次启动都会问 "Trust this folder?"，且
  "Don't trust" 的语义是直接退出（不是继续运行）——唯一的继续路径是选 Trust。
  有 `.mcp.json` 的目录还会列出要启用的 MCP targets，需一并确认。
- **就绪判据**（实测）：kimi 的输入框 `│ > │` 出现，**且**状态行出现
  `Ask When Needed  K3 thinking: high`。

用 `cmux read-screen` 逐席确认过门且就绪后才进入 Phase 1。建院时记录每个席位的
就绪耗时，作为后续超时预算的依据。

**Phase 1 分发 brief**

```bash
cmux send --workspace "senate/$RUN/seat-a" "读取 $RUN/brief-a.md 并执行"
cmux send-key "senate/$RUN/seat-a" Enter        # send 不提交，必须补 Enter
```

或用 socket API `workspace.prompt_submit`（需 `workspace_id`；确切参数未验证，见第九节）。

**Phase 2 收集屏障** ✓ 实测跨进程可用

主席的 Bash 是同步的，直接在会话里跑 `wait-for` 会把自己阻塞掉、丧失干预能力。
等待必须**后台执行**，主席轮询而非阻塞：

```bash
# 三个席位的等待以后台任务并行启动（主席工具的 run_in_background，或 nohup 落盘）
cmux wait-for "senate/$RUN/seat-a" --timeout 1200   # 后台
# 主席每 60s 轮询一次：后台任务状态 + proposals/ 产物文件是否出现
```

默认轮询周期 60s、屏障超时 1200s；轮询间隙正是主席发起中途干预的窗口。

议员 brief 的最后一步固定为：

```bash
cmux wait-for -S "senate/$RUN/seat-a"
```

把"完成检测"从技术问题变成协议问题——这反而是 cmux 拓扑下更可控的一点：信号是议员
主动发的，没发就是没干完，超时即缺席，不需要启发式地猜屏幕。

超时后不要立刻判缺席，先取证：`cmux read-screen --surface <seat> --lines 200` 落盘到
`$RUN/forensics/seat-a.screen`，再判。这份现场是事后复盘为什么这席挂掉的唯一线索。

**Phase 3–5 归并计票**：主席受限操作，无 cmux 参与。判重是语义判断，只发生在同
anchor 文件的预分组内部；乱序由主席跑脚本做真实随机（`shuf` 或等效），不靠
"感觉打乱"。归并必须满足**条目守恒不变量**：
`len(items) + len(dropped) == 三席提案条目总数`，且 `dropped` 每条必须写明丢弃
原因——这是让归并可审计的唯一手段。

**Phase 6 执行**

```bash
# 一次只下发一条
cmux send --workspace "senate/$RUN/executor" "执行 $RUN/work/I-004.md"
cmux wait-for "senate/$RUN/exec-I-004" --timeout 600
cmux diff --source branch          # 给人类看总账
```

**Phase 7 闭院**：席位 workspace **保留不关**。审计价值高于资源成本，人可能要回看
某个席位的推理过程。用 `cmux workspace status set lane` 归拢而非关闭。

可选的可观测性增强：把通过条目写进占位符 `cmux todo add`，让人在侧边栏直接看到议程；
完成时 `cmux notify` 提醒。

## 四、文件协议

通信全部走文件，不走 stdout——三个 harness 的输出格式互不兼容（kimi 的 text 模式还会
掺 `To resume this session: ...` 之类的尾巴）。stdout 只当逃生舱。

```
<repo>/.senate/<run-id>/
├── brief-a.md / brief-b.md / brief-c.md   # 主席 → 各席位（handoff）
├── proposals/seat-a.json                  # 席位 → 主席
├── items.json                             # 归并后的条目池（含原始出处）
├── ballots/seat-a.json                    # 匿名乱序后发给投票者的版本
├── votes/seat-a.json                      # 席位 → 主席
├── tally.json                             # 计票结果 + 匿名映射揭示
├── forensics/seat-a.screen                # 超时席位的现场快照
├── work/I-004.md                          # 下发给执行者的工单
└── report.md                              # 最终报告
```

### brief（席位收到的全部指令）

一份 brief 包含六段，缺一不可：

```markdown
## 任务
对本仓库做健康巡检，找出可被机械执行的优化点。

## 你的视角
<每个席位不同，见第五节>

## 范围
<默认收窄到活跃面或用户指定路径>

## 输出契约
写 JSON 到 .senate/<run>/proposals/seat-a.json，schema 见下。
最多 8 条，按 severity 降序。

## 硬性要求
- 每条必须有 anchor（file:line 或 file:symbol），主席会验证该位置存在；
  无 anchor 的条目直接丢弃，不进入投票。
- executable 字段自评：这条能否被一个普通模型机械执行。
  拿不准就填 false，它不会丢，只会转到人工通道。
- 不要写"增加测试""改进文档"这类无锚点的建议。

## 完成信号
写完文件后执行：cmux wait-for -S "senate/<run>/seat-a"
```

### 提案条目 schema

```json
{
  "seat": "a",
  "items": [
    {
      "title": "≤80 字，一句话",
      "severity": "critical | major | minor",
      "category": "correctness | concurrency | api | perf | docs",
      "anchor": "src/main/java/.../Par.java:142",
      "claim": "现状是什么，为什么是问题",
      "change": "要改什么——原子、机械可描述",
      "acceptance": "怎么验证——可执行命令或可观察断言",
      "probe": "为确认该问题实际执行过的命令及其输出摘要；只读无命令的条目填 null",
      "executable": true
    }
  ]
}
```

### 投票条目 schema

```json
{
  "seat": "a",
  "votes": [
    {
      "id": "I-004",
      "vote": "YES | NO | ABSTAIN",
      "evidence": "file:line 锚点，或命令 + 实测输出",
      "reason": "≤200 字"
    }
  ]
}
```

**`evidence` 是必填项，不是补充说明。** 没有证据的 `YES` 在计票时自动降级为 `ABSTAIN`。
这条规则把投票从"三个直觉取多数"变成"证据聚合"，是整套机制里防止顶级模型互相点头的
唯一有效手段。没有它，你会得到一份看起来很权威、实际零验证的清单。

**证据必须被验证，不只是被要求。** 计票前主席逐条核验 `YES` 票的 evidence：anchor 类
用 grep/读文件确认该位置存在且内容与 claim 相符；命令类证据要求粘贴原样输出，主席
抽查复跑。验证不通过的 evidence 视同无证据——该票降级 `ABSTAIN`，并在 `tally.json`
记为 `evidence_invalid`。

## 五、视角分化：对抗相关性错误

三个顶级模型读同一份代码、拿同一份 prompt，它们的错误是**相关的**，不是独立的。多数
投票在错误独立时有效，在错误相关时几乎无效——同一批训练数据、同一套流行观点，会让它们
整齐地漏掉同一个 corner case，然后 3:0"一致通过"。1+1+1 ≈ 1。

**提案必须分化，投票必须聚合。** 召回率由视角分化保证，精度由交叉投票保证。

三个 lens，覆盖同一个巡检面、但关注点不重叠：

| 席位 | lens | 关注 |
|---|---|---|
| A | 并发正确性 | 竞态、内存可见性、取消路径、状态机终态 |
| B | 公共 API 与契约 | 签名一致性、向后兼容、调用方影响面、文档与实现是否相符 |
| C | 资源与异常路径 | 生命周期、泄漏、错误传播、边界值、测试盲区 |

关键：**席位不被告知其他席位拿的是什么 lens**。知道"C 在管边界值"会让 A 偷懒。
**lens → 席位的映射每轮随机轮换**（本轮 A 拿并发，下轮可能拿资源）——固定映射会让
"并发条目必出自 A"成为跨轮次可学习的指纹，轮换使这种题材溯源不可学习。

三席都会对所有条目投票，包括自己没找过的方向——这正是交叉验证的价值所在。因为每条
投票都要求证据，A 对 C 提的边界值问题也必须实际去读那段代码才能投 YES。

## 六、健康巡检特有的约束

"读代码库找优化点"这个输入有两个天然失败模式，必须在设计层面对抗。

### 失败模式 1：语义稀释

没有 diff 作为锚点，三个模型都会吐出"增加测试覆盖""改进错误处理""考虑补充文档"这类
**无法执行、彼此雷同**的条目。三条对策，按作用强度排序：

1. **无 anchor 即丢弃。** 每条必须有 `file:line` 或 `file:symbol`，主席验证位置真实存在
   （用 grep 或读文件确认）。这一条单独就能过滤掉绝大多数空话。
2. **条数封顶（每席 8 条）。** 强制排序即强制取舍。这是对抗稀释最有效的手段——给模型
   无限配额，它就会把能想到的都列上；给 8 条，它才必须判断什么重要。
3. **`executable=false` 不占投票配额。** 架构级建议不丢，但走人工通道，不与可执行条目
   争夺注意力。

### 失败模式 2：范围爆炸

"全代码库巡检"必然稀释——仓库越大，条目越浅。默认策略：

- **默认收窄**到活跃面：最近 N 次提交触达的文件（`git log --since` 求热点），
  或用户显式指定的路径。
- **全库巡检是显式选项**，不是默认行为。选它就要接受更长的超时和更低的条目密度。

用户的提示词可以直接覆盖范围（"只看取消路径相关的代码"），此时该提示词进入所有
brief 的「范围」段，但**lens 分化照常**——缩小范围不等于取消分化。

## 七、计票与法定人数

```
在场 = 发出了完成信号 且 产物通过 schema 校验的席位
分母 = 在场席位
门槛 = floor(分母 / 2) + 1        # 严格过半
ABSTAIN 计入分母，但不计入赞成
无证据或证据核验不通过（evidence_invalid）的 YES 按 ABSTAIN 计   # 见第四节
```

**进入投票的条目池封顶 12 条。** 归并后超出部分按 severity 降序、同级按"提出该问题的
席位数"降序截断；被截断的条目不进 ballot，写进报告的"未表决"区。

| 在场 | 通过门槛 | 行为 |
|---|---|---|
| 3 | ≥2 | 三席模式：正常执行 |
| 2 | ≥2（即必须一致） | 两席模式：**一等运行模式**，报告标注 `quorum=2, advisory`；`severity=critical` 的条目不予执行，只进报告 |
| 1 | — | 终止本轮，议会无意义 |
| 0 | — | 终止，报错退出 |

两席模式不是异常分支，是当前默认配置下的常态。两种模式的实质差异：三席模式允许一票
反对下仍通过；两席模式必须一致，且 critical 条目一律不执行——它的产出定位是"建议
清单"而不是"修复流水线"。

**缺席必须显式记录。** 报告里要写清楚哪一席缺席、超时还是产物不合格、现场快照在哪。
静默按在场人数计票是最危险的失败方式——报告看起来完全正常，实际门槛已经变了。

保留原始票：`votes/*.json` 与 `ballots/*.json` 都留档，`tally.json` 记录匿名映射的
揭示。事后要能回答"这条到底是谁提的、谁投的、凭什么投的"。

### 可选澄清轮

cmux 拓扑独有的能力，**默认关闭**：对 `vote=YES 但 evidence 为空`的条目，主席退回该席位，
要求补证据或改票。只做一轮，不辩论。开启它会显著拉长一轮议会的时间，收益仅在对该轮
结论信心不足时体现。

## 八、执行与成本

### 执行纪律

- **一次只下发一条**，执行完立刻跑该条的 `acceptance`。
- 验收失败 → **立即停止并回报**，不要"顺手修一下"。廉价模型越修越糟。
- 连续 3 条失败 → 终止，升级给人类。
- `executable=false` 的通过条目不进执行队列，落进报告的"待人工决策"区。

后两条的理由是同一个：执行者的判断力是这套流水线上最弱的一环，任何需要它临场判断的
地方都应该停下来交给人。

### 成本模型

一轮完整议会 = 3 席 × 2 轮（提案 + 投票）+ N 条执行。实测一次 Opus trivia 调用约
$0.068；真实仓库巡检的提案轮大概率 $1–5/席。投票轮是 `ballot 条数 × 在场席位数` 次
带证据核查（封顶 12 × 3 = 36 次），单次核查与提案轮同量级——预算时不能漏掉这一半。
所以默认值取保守：

- 提案超时 1200s，投票超时 600s，执行超时 600s
- 每席提案封顶 8 条
- 默认不开澄清轮
- 巡检范围默认收窄

**cmux 拓扑下没有金额硬闸门**（`--max-budget-usd` 只对 `--print` 生效）。替代手段是
可观测性本身：`cmux top --processes` 看资源占用，`cmux tree` 看谁还在跑，人在 UI 里
随时能叫停。这是选 cmux 换来可追问能力的代价，需要在建院前就接受。

## 九、失败模式与对策

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 相关性错误 | 三席整齐漏掉同一个 corner case，3:0 通过 | 视角分化（第五节） |
| 礼貌性点头 | 三票 YES 全无证据 | evidence 门槛，无证据降级 ABSTAIN |
| 共识伪装正确 | 高票条目执行后引入 bug | 执行后强制跑 acceptance；共识只是排序，不是正确性 |
| 提案污染 | 席位看到了别人的提案再投票 | Phase 1/4 之间硬屏障，匿名 + 乱序 ballot |
| 自我偏好 | 席位倾向自己提的条目 | ballot 去署名 + 随机 seat 标签重映射 + lens 每轮轮换；只消除自我偏好，不消除题材溯源——lens 分化决定了一条"并发"提案必然来自拿并发 lens 的席位，匿名藏的是署名，不是题材 |
| 语义稀释 | 条目全是"加测试""改文档" | 无 anchor 即丢弃 + 条数封顶 |
| 静默降级 | 缺一席，门槛悄悄变成一致同意 | quorum 显式判定 + 报告标注 + 现场取证 |
| 执行跑偏 | 廉价模型自由发挥 | 一次一条 + 验收 + 失败即停 |

### 一条自我反驳

**"三个顶级模型投票"不产出正确性，只产出共识。** 共识和正确是两回事——三票一致通过的
错误，比一票提出的错误更危险，因为它披上了权威的外衣。

这套设计里真正提供正确性的是三样东西：视角分化（对抗相关性错误）、证据门槛（对抗
礼貌性点头）、执行后强制验收（对抗前两者的残余误差）。投票只是决定"先做哪条"的排序
机制。

因此有一条哨兵规则，判据可操作：**若三席提案的 anchor 集合 Jaccard 重叠 > 0.7
且 `probe != null` 的条目占比 < 20%，判该轮退化，不进入投票。** 两个数字由主席
跑脚本计算，不靠感觉。那不是议会运转良好，那是三个模型读完同一份 prompt 后复述了
同一段话。
