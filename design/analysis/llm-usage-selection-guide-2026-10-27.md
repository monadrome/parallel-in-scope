# LLM 选型方法论（2026-10）

- 日期：2026-10-27
- 定位：一份**可重复执行的选型决策流程**，不是某次选型的结论。文中出现的价格、榜单数据只作例证，完整数据来源见附录 A–D。
- 读者画像：需要为自己的项目/团队挑选并长期使用 LLM 的开发者。不需要任何 ML 背景。

## 引言：为什么选型需要方法论

模型每隔几个月换代一次，任何「2026 年 10 月该选哪个模型」的答案都会过期；但「怎么选」的流程不会。这份文档只回答后一个问题。

选型失败极少是因为「模型太差」，几乎总是因为以下三种错误之一：

1. **没定义任务就选模型**——典型如「拿旗舰模型写给人读的文章」：模型本身没坏，是任务画像与模型特长错配。
2. **把单一榜单当真理**——榜单之间经常互相矛盾，因为它们量的根本不是同一件事；不看打分者是谁就采信排名，等于听信一个利益相关方的一面之词。
3. **选完就裸用**——每个模型都带着训练留下的已知习惯（好的坏的），不针对性调整系统提示，就把「可以提示词缓解的毛病」误判成「模型不行」，又把「提示词根本救不了的毛病」浪费在反复改提示词上。

整个流程可以类比为**招聘**：任务画像就是岗位描述（JD），榜单筛选是简历初筛，自建评测是面试，特性适配是入职引导，版本锁定是合同与试用期。跳过任何一步，都会在下一步付出代价。

流程共六步：**画像 → 档位初筛 → 证据三角化 → 自建小评测 → 特性适配 → 锁定与治理**。

## 第 0 步：任务画像——先定义问题，再看模型

**这一步防止的错误**：任务与模型错配。后面所有步骤的输入都是这张卡；跳过它，后面每一步都在猜。

给任务建档，逐项回答：

| 维度 | 问自己 | 为什么重要 |
|---|---|---|
| 任务类型 | 交互编码 / 批量抽取 / 长程 agent / 写作 / 判断评审？ | 不同类型在不同模型上是完全不同的排名 |
| 延迟 | 实时交互，还是可以等几小时？ | 可以等 = Batch API 直接五折，预算档位整个下移 |
| 批量 | 单次调用，还是每天百万级？ | 量级决定对单价的敏感度，百万级下 10 倍价差就是 10 倍成本 |
| 错误代价 | 错了能自动校验补救，还是一次错误毁掉交付？ | 只有后者才值得为旗舰付 100 倍价差 |
| 语言 | 中文、英文还是混合？ | 英文榜的排名对中文任务基本不作数，能力是分语言的 |
| 确定性 | 需要每次输出严格一致吗？ | 需要的话要靠结构化输出机制，而不是赌采样 |
| 成本上限 | tokens × 单价 × 步数，总量粗算是多少？ | 先有预算刻度，才谈得上「贵不贵」 |

**产出：一张任务规格卡。** 本文用三个例子贯穿全程，画像各不相同：

- **例 A**：每晚批量抽取 100 万条工单字段。高吞吐、可离线、产出可自动校验。
- **例 B**：交互式结对编程与设计讨论。延迟敏感、长会话、需要判断力。
- **例 C**：中文日常技术对话，要求「像人说话」。（这正是 Kiro session `sess_7322f601` 的原始场景：用户抱怨 GPT-6 Astra / 6.1 Sol 「不说人话」。）

## 第 1 步：档位初筛——经济学先于榜单

**这一步防止的错误**：默认买最贵最新的。同一家厂商内部，旗舰与最低档的价差可达 **100 倍**（如 Astra $10/$50 vs Luna $0.10/$50 区间的 Luna $0.10/$0.50），而多数日常任务在中档模型上已经达标。反过来想：**升档随时可以，买旗舰省不回来**——如果中档不行，升级的代价只是重跑一次；但如果默认旗舰，多花的钱每一步都在发生。

三条规则：

1. **默认中档**。只有两种情况才动旗舰：中档 + 高 effort 实测仍不达标，或错误代价高到不容许失败（如架构级重构的一次性交付）。
2. **可校验的批量任务走最低档**。抽取、分类、路由这类任务，输出可以逐条机器校验（schema 合规、字段非空、枚举合法），错了能自动兜住，就用最便宜的档位，把预算花在校验器而不是模型上。
3. **级联（cascade）架构**：便宜模型跑全量，校验器分诊，只把失败子集升级给贵模型重跑。这是批量任务的标准形态——大部分输入简单，贵模型只需要处理少数难例，总成本接近「全量 × 低价 + 少量 × 高价」。

关于 **effort（推理强度）**：它是独立于模型选择的第二个旋钮，控制模型「思考」的深度。两个常见误区：一是简单任务开高档——只会更慢更贵，还会想多了跑偏；二是指望用高档救风格类问题——GPT-6 的对话毛病在所有 effort 档位都存在，旋钮不对症。正确用法：从中档模型的默认档起步，实测不达标再加档。

**例 A**：Luna / Haiku 5.5 + Batch 五折起步，小样本测抽取准确率，失败子集升 Sol/Sonnet 重跑。
**例 B**：Opus 5.5 / Sol 中档起步；架构级重构才考虑 Fable 5.1 / Astra。
**例 C**：纯对话任务，中档绰绰有余——「最新最贵」在这个画像下不提供任何加分项。

## 第 2 步：证据三角化——读榜的方法，不是背榜的结论

**这一步防止的错误**：把单一榜单当真理。公开榜单有用，但用之前必须问三个问题，缺一不可。

**问题一：谁在打分？**
评委分两种，结论可以完全相反：

- **LLM 当裁判**（如 EQ-Bench 创意写作）：快、便宜、可规模化，但有**家族自偏好**——实证研究里 GPT-4 能以 73.5% 的准确率认出哪些输出是自己的，而且自识别能力越强、偏爱自家输出越明显。让 Claude 给各家文章打分，Claude 系天然占优。
- **人类盲投**（如 arena.ai）：贵、慢，但量的是「真人读了舒不舒服」。

**例 C 的关键证据就在这里**：GPT-6 Astra 的写作，EQ-Bench（Claude 当裁判）排第一，arena.ai 人类盲投只赢 38/414。这个矛盾本身就是信息——机器裁判欣赏它的结构与完整性，人类嫌它腔调不自然。你的任务要哪个，就取信哪个：任务 = 给人读的对话，取人类票；任务 = 长篇结构化生成且有人工终稿，机器榜 + 自测更相关。

**问题二：分布覆盖我的任务吗？**
公开榜测的大多是英文创意写作。中文能力、技术对话、你业务领域的具体任务，都不在分布内。中文场景要看中文榜（当前一线是 MiMo-V2.6-Pro / Kimi K3 / Qwen3.8 Max 一线，见附录 B），英文总榜对中文任务的参考价值接近零。**「文学性」和「像人说话」是两个不同的指标，分开查、分开选。**

**问题三：这个榜被污染了吗？**
公开 benchmark 的测试题会进入下一代模型的训练数据（实证：MMLU 约 29%、C-Eval 约 46% 的测试项有污染迹象），导致分数系统性虚高。这是公开榜的固有缺陷，无法从榜内修复——所以它只能做初筛，终审在下一步。

三条问完，得到的是**候选名单**（2–3 个模型），不是最终答案。

## 第 3 步：自建小评测——终审权在自己手里

**这一步防止的错误**：把初筛当终审。公开榜是别人出的题；你的任务只有你自己能出题。这也是整个方法论里**性价比最高**的一步——20 个真实问题、一个下午的盲读，就能替代数小时的榜单考古。

方法五条，每条对应一个坑：

1. **样本源自真实工作**：10–20 个日常真实问题或历史失败案例，不要编「看起来很测试」的题。自建集因为不在任何训练数据里，天然免疫污染，而且直接对齐你的业务分布——这两点恰是公开榜的死穴。
2. **多模型 × 多次运行**：同一 prompt 跑 2–3 遍。LLM 输出有非确定性，一稿定结论是抽签；ToneBench 让每个模型每题写 5 稿，就是承认「一稿可能是运气」。候选模型全部打乱编号，盲读。
3. **断言与人判两层**：能自动判定的写断言（schema 合规、关键事实正确、禁词命中——比如 slop 黑名单词出现即扣分），主观质量靠人盲读。客观分数可以再叠一个工具分（如 Slop Score）作参照。
4. **失败回灌**：日常使用中不满意的输出，事后补进 eval 集。集子随真实痛点滚动生长，越用越准。
5. **记录响应里的 `model` 字段**：防静默路由——有社区抓包投诉称约 15% 的 Astra 请求实际返回了 Luna。不记录，你无法区分「模型不行」和「根本不是那个模型」。

**重跑触发器**（把 eval 当回归测试，不是一次性考试）：换模型、升版本、改系统提示、改规则文件，任何一项发生就重跑。

**例 C 落地**：15 个真实技术问题 × 3 个候选 × 3 遍，打乱盲读 + Slop Score 客观分。这套东西跑下来，「Astra 不说人话」就从主观抱怨变成了可复现的淘汰证据——这正是方法论的意义：**把体感变成证据**。

## 第 4 步：模型特性适配——选完才是开始

**这一步防止的错误**：选完直接裸用。每个模型都带着训练留下的已知习惯——对冲风险被奖励过，所以说话带免责声明；「看起来全面」被奖励过，所以篇幅膨胀。这些不是缺陷，是训练目标的副作用，而且**大多可以用系统提示针对性缓解**，官方甚至会主动发缓解指南（OpenAI 就为 Astra 发过官方提示词指南，含 slop 词黑名单）。

具体做法：为每个选定的模型维护一张 **特性 → 反制对照表**，落成一份 prompt profile（系统提示/规则文件），**当版本化代码管理**——因为模型换代后它可能静默失效，换模型 = 一次回归测试。

本次调研证实的对照表（可直接抄用）：

| 模型/特性 | 已知问题 | 反制写法 |
|---|---|---|
| Astra：slop 腔 | 官方黑名单词（"delve"、"it's worth noting"、"This isn't about X. It's about Y"、"In short:"、自造连字符词）；偏爱列表/表格/Markdown；跨会话重复措辞 | 黑名单逐条写进系统提示；明确要求「用段落、主动语态」 |
| Astra：行动犹豫 | 爱停下来问澄清问题；对含糊或矛盾的指令文件敏感，会卡住不动 | 注入 "bias towards action"（偏向直接行动）段；规则文件去矛盾、显式写优先级；出问题时要求它说出被哪条规则卡住 |
| Astra：安全分类器 | 漏洞利用类请求被前置分类器拦截，声明有授权也没用 | **提示词救不了——这是选型条件**：安全研究类任务直接换模型或换流程 |
| Sol 6.1：过度压缩 | 上一代一次能给够的深度，这代要追问好几轮 | 显式要结构：「先给结论，再展开完整论证，不省略步骤」；写明期望长度 |
| Claude 系：谄媚 | 顺着用户说；矫枉过正时表现为 argumentative、难认错 | Ask, Don't Tell——把断言改成问句求证，不要用陈述句求认同；明写「直接指出我的错误」（比 "be critical" 可靠：后者下模型发现错也可能不说） |
| 通用：长对话漂移 | 多轮之后准确率下降、风格指令失效、开始重复 | 规则放 system prompt 而非聊天里说一次；定期令其复述约束；一个任务一个会话，换会话时写摘要交接 |
| 通用：默认格式 | Markdown 轰炸 | 产出要进 commit message、邮件、文章时，显式指定格式 |
| 通用：自我汇报不可信 | 「测试全过」不算数 | 规则要求每个完成声明附可核对的产物；验收只认 git diff、测试输出 |

写法上的三条经验，都有实证或官方佐证：

1. **负面约束为主**——约束文件里约八成条目写「禁止什么」。原因：正向形容词（「简洁」「自然」）对模型是模糊指令，禁令（「不要用‘值得注意的是’开头」）是可执行指令。
2. **配本人范文**——拿一段你自己写的文字做样例。风格难以用语言精确描述，但极易模仿；给实例比给形容词精确得多。
3. **读厂商的模型专属提示指南**——OpenAI 为 Astra 发过官方指南，第一手反制清单是免费拿的；换模型时先查有没有对应文档。

**本步最重要的判断**：分清两类毛病。**提示词可缓解的**（slop、犹豫、压缩、谄媚）——调 prompt，别急着淘汰模型；**机制才能兜住的**（安全分类器拦截、非确定性、截断、越权动作）——改提示词是浪费时间，要么换选型，要么上工程手段（校验、幂等、权限）。把两类混为一谈，就会在该换模型时空耗提示词，在该调提示词时冤枉模型。

## 第 5 步：锁定与治理——让结论保持有效

**这一步防止的错误**：今天测好的组合，三个月后悄悄变坏。模型行为会漂移，供应商会静默更新、会弃用、会路由；不做治理，第 3 步的评测结果会无声过期。

- **pin 版本**：OpenAI 用 dated snapshot ID（family alias 会被指向新快照）；Anthropic 从 4.6 代起无日期 ID 本身即 pinned snapshot，不漂移。所有评测与生产统一用快照，保证可复现。
- **订阅弃用通知**，升级前重跑自建 eval——这一条把「升级」从赌博变成回归测试。
- **成本治理**：每个 agent 任务设 token/步数硬预算（agent 循环失控烧钱没有自然刹车）；静态内容（工具定义 → system → 文档）放 prompt 前部、动态内容放尾部，保住缓存命中（agent 场景缓存命中是最大省钱项）；时间戳和 effort 参数不要混进前缀——会打穿缓存。
- **工程兜底**：消费响应前查 `finish_reason`/`stop_reason`（截断是静默的，半截 JSON 不报错）；结构化输出与工具定义能 `strict` 就 `strict`，边缘仍留 schema 校验；有副作用的动作（写文件、发请求）配幂等键，因为 SDK 默认会自动重试。

## 完整走一遍：例 C（Kiro 场景重演）

原始场景里，用户直接拿了旗舰模型写给人读的中文对话，然后忍受了一段时间的「不说人话」。同一场景过一遍流程：

1. **画像**：中文技术对话、要像人说话、单次交互、成本不敏感。
2. **档位**：对话任务中档足够 → Opus 5.5 / Sol / GLM-5.3 入候选，旗舰在画像阶段就出局。
3. **三角化**：「像人说话」对应人类盲投 → arena 人类票为主（Opus 5.5 第一）；EQ-Bench（机器裁判）只当参考；再叠中文榜。
4. **自测**：15 个真实问题 × 3 候选 × 3 遍盲读 + Slop Score。
5. **适配**：选定后注入——slop 黑名单 + 禁说教前导与免责声明 + 「直接纠错」条款 + 期望长度。
6. **锁定**：记录 model id，季度重跑 eval。

原始错误会在第 0 步（任务画像与「旗舰」逻辑错配）就被拦下；即便放行，第 2 步（人类票 38/414）或第 4 步（自测不满意）也会拦住，且每一步都留下可复现的证据。

## 反模式清单

- 按「最新 / 最贵 / 总榜第一」选（跳过画像与档位）
- 只看一个榜，不看打分者是谁（跳过三角化）
- 一次运行下结论（无视非确定性）
- 选完直接裸用（跳过特性适配）
- 公开榜当终审，没有自建 eval（初筛代替面试）
- 提示词一次调好永不回归（模型换代后静默失效）
- 把「提示词可缓解的毛病」和「机制才能兜的毛病」混为一谈（错误的开方）

## 方法检查清单

```
画像规格卡（7 维度）            □
档位成本模型 + 级联设计          □
三角化：≥2 个榜，各自打分者已确认 □

```

## 附录 C：API 机制层

约定：`A=` platform.claude.com/docs/en，`O=` developers.openai.com/api/docs/guides（platform.openai.com/docs 已 301 迁移至 developers.openai.com）。未标【社区】的均为官方文档。

### 1. Prompt caching

- Anthropic（A/build-with-claude/prompt-caching）：显式 `cache_control` 断点（≤4 个）；层级 tools → system → messages，改任一层即失效其下全部；最小前缀按模型 512–4096 tokens；写 1.25×（TTL 5 分钟）/2×（1 小时），读 0.1×（部分新模型低至 0.05×/0.025×）。
- OpenAI（O/prompt-caching）：全自动；GPT-5.6+ 前缀 ≥1024 tokens；读 0.1×、写 1.25×（30 分钟）/2.5×（12 小时）；工具 schema、structured outputs、reasoning effort 任一变化即 miss。
- 坑与布局：前缀须完全一致——时间戳混入、改思考参数（budget/effort）都会打穿缓存（两家官方均点名）；静态内容（工具/系统/文档）在前、动态后缀在后。差异：Anthropic 显式断点 + 可选 1h TTL + 可预热；OpenAI 自动、不可控。

### 2. Reasoning 计费

- 官方：两家思考 token 均按输出价计费且占上下文。OpenAI（O/reasoning）：token 不可见；effort 分 none–max 档（GPT-5.5 默认 medium）；官方建议起手预留 ≥25k tokens；store:false 下工具调用须回传加密 reasoning，成本上升。Anthropic（A/build-with-claude/extended-thinking）：`budget_tokens` 于 4.6 代弃用、4.7+ 直接返回 400，改用 adaptive thinking + `output_config.effort`；思考 >32k 官方建议转 Batch 防超时。
- 【社区】思考可占输出 50%+（实测案例 55.8%），复杂任务总成本可达普通 3–10 倍。

### 3. 截断

- 官方（A/build-with-claude/handling-stop-reasons）：`stop_reason=max_tokens`（OpenAI 为 `finish_reason=length`）= 响应被截断、不完整；典型后果是半截 JSON、缺参数的 tool_use。官方要求：max_tokens 宽裕设置、消费前必查停止原因；工具块被截断必须加大额度重发。
- 【社区】长输出另靠任务分段或 continue 拼接，拼接有丢上下文风险。

### 4. 结构化输出与工具调用

- 官方：OpenAI（O/structured-outputs）`strict:true` 约束解码，保证输出符合 JSON Schema；首个请求有 schema 编译延迟；JSON mode 只保证合法 JSON 不保证 schema。Anthropic（A/agents-and-tools/tool-use/strict-tool-use）工具定义 `strict:true` 用 grammar-constrained sampling 保证参数严格合规、工具名必有效。
- 官方承认幻觉：非 strict 时 Sonnet 可能 "guess values you didn't supply"（A/agents-and-tools/tool-use/overview）。
- 【社区】头部模型工具参数幻觉率约 1.3–1.9%（平均从 2021 年 ~38% 降至 2026 年 ~8.2%）；缓解：工具版本化、边缘校验 + 结构化错误回传。

### 5. 重试与幂等

- 官方：两家 SDK 默认 `max_retries=2`、短指数退避，自动重试连接错误/408/409/429/≥500；429 按响应头 retry-after 加抖动；配额型 429（OpenAI insufficient_quota、Anthropic spend limit）重试无效。OpenAI 提供 Idempotency-Key（保留 24h），Anthropic 无。
- 【社区】agent 副作用动作（下单/发邮件）被重试即重复执行：需幂等键或人工确认。

### 6. Batch API

- 官方：两家均 5 折。OpenAI（O/batch）24h 内完成（常更快）、单批 ≤5 万请求/200MB、独立限流池；Anthropic（A/build-with-claude/batch-processing）多数 <1 小时、单批 ≤10 万请求。适用：非实时评估、分类、嵌入。

### 7. 版本锁定

- 官方：OpenAI（developers.openai.com/api/docs/deprecations）dated snapshot 有弃用公告 + 关停日（GA 模型一般约 6 个月）；chatgpt-4o-latest 为滚动 alias，持续更新、面向研究评估、不建议生产，且已被后继替代弃用。Anthropic（A/about-claude/model-deprecations）弃用提前 ≥60 天通知；alias 随升级指向新快照，dated snapshot 行为固定；参数级弃用也已出现（temperature/top_p/top_k 已随 2026-10-21 API 版移除）。

## 附录 D：agent 安全与评估

### 1. Prompt injection 防御现状

- [证] OWASP LLM Top 10 2025 把 Prompt Injection 列为 LLM01 首位风险，明确覆盖 indirect injection（外部网页/文件/工具输出中藏指令劫持会话）：genai.owasp.org/llm-top-10/
- [证] 微软 Spotlighting 论文（delimiters/datamarking/encoding 三种数据-指令分离变换）将注入攻击成功率从 >50% 压到 <2%：arxiv.org/abs/2403.14720
- [搜] EchoLeak（CVE-2025-32711）对 M365 Copilot 的零点击注入导致数据外泄，是 indirect injection 的标志性实战案例
- [识] 公认防御栈：最小权限（缩小 blast radius）、处理不可信输入的组件与执行动作的组件物理隔离、工具白名单 + 输出校验、高危操作人工确认、完整审计日志。结论共识是「无单一防御足够，必须纵深防御」

### 2. LLM-as-judge 偏差证据

- [证] 自偏好：GPT-4/Llama-2 能「认出」自己的输出（GPT-4 达 73.5%），且自识别能力与自偏好强度线性相关：arxiv.org/abs/2404.13076
- [证] 位置偏差：仅调换候选顺序，Vicuna-13B 就能在 80 题中的 66 题「击败」ChatGPT（Large Language Models are not Fair Evaluators）：arxiv.org/abs/2305.17926
- [识] 长度/详尽偏差：评委系统性偏爱更长回答，缓解靠 rubric 明确惩罚冗余
- [识] 缓解组合：评委换厂商/异构模型、盲测 + 随机顺序、正反双评取均值、维护人工金标集定期校准

### 3. Benchmark 污染

- [证] 泄漏实证：对 31 个模型的基准泄漏研究（JHU/NAACL 2024），并提出 Benchmark Transparency Card；MMLU 约 29.1%、C-Eval 约 45.8% 测试项有污染迹象：arxiv.org/abs/2404.18824
- [搜] 分数虚高：干净版 GSM8K 重测 Mistral 掉约 13 分；2025 年末综述估计膨胀 6%–40%
- [证] 自建 eval 方法论（Hamel Husain）：从真实失败案例起步，bite-sized 任务 + 断言自动判定，三层递进（断言单测 → 人工看 trace → A/B），持续用失败回灌；核心理念「不看大量数据就是做错了」：hamel.dev/blog/posts/evals/
- [识] 自建集不出现在训练数据里，因此不受污染影响，且直接对齐自家业务分布

### 4. Agent 成本控制

- [搜] Gartner 2026.3 分析称 agent 任务 token 消耗为普通 chatbot 的 5–30 倍；主因是每步循环重发系统提示、工具定义与全量历史（未核对原报告，仅搜索转述）
- [证] Compaction 的信息损失有官方警告：Anthropic 明确指出「过度压缩会丢失当时不起眼、事后才显关键的细粒度上下文」，建议从原始记录而非摘要再摘要派生压缩，先保 recall 再调 precision：anthropic.com/engineering/effective-context-engineering-for-ai-agents
- [证] 会话拆分权衡：同文建议 sub-agent 用干净上下文做长探索、只回传 1–2k token 摘要给主 agent（隔离噪声但丢失跨段细节），以及结构化笔记（NOTES.md/TODO）外置记忆
- [识] 实操：prompt caching、按步数/token/工具调用设硬预算、成本归因到工作流

### 5. 自我汇报不可靠

- [证] Anthropic 工程实践：「LLM 不总说自己真实意图」，要求审查原始 tool 转录而非模型自述；官方示例中评估团队从原始 transcript 发现了模型 CoT 里没提的问题：anthropic.com/engineering/writing-tools-for-agents
- [识] 验证以产物为准：git diff、测试通过/失败输出、构建日志、实际 API 返回是可复核信号；agent 说「测试全过」不算数，跑一遍才算数
