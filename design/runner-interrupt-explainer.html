parallel-in-scope / runner 退出协议

中断的是线程，取消的是任务

A 保存下来的 worker 引用仍然指向同一条线程。但等中断真正投递时，这条线程可能已经开始执行 B。

根因：清空引用并不撤回已经读到的引用

runner = null 只影响后续读取。取消线程已经保存的局部变量 executing 不会随之变成 null。volatile 保证可见性，却没有把“读取 → 投递”变成一个不可分割的操作。

worker 在 A 与 B 之间清一次中断标志也无效：中断可以在清理之后才到达。再检查一次 runner 也无效：检查之后仍可暂停。

推荐协议：投递先登记，退出等交接

取消侧必须在读取 runner 之前登记；退出侧必须在等待 之前撤销 runner，并在等待结束后才恢复线程标志。

// 共享字段
volatile Thread runner;
volatile boolean delivering;

// interruptTask()
delivering = true;
try {
    Thread t = runner;
    if (t != null) t.interrupt();
} finally {
    delivering = false;
}

这是最小协议示意，沿用 FutureTask 的在途投递等待思路。它不改变取消归因，也不需要增加公开 API。

// run() 的退出路径
runner = null;
while (delivering) {
    Thread.yield();
}

// 然后完成其余清理，恢复入口标志
restoreEntryInterruptState();

// 最后返回执行器，worker 才可运行 B
示意省略了 @Nullable、现有 phase 通知与上下文恢复。restoreEntryInterruptState() 是说明用名称。

为什么这能覆盖两种竞争顺序？

  • 取消先拿到 worker：登记投递 → 读到 worker → 退出侧清空 runner → 退出侧看到投递中，等待 → 投递结束 → 恢复标志 → B。中断无法迟到到 B。
  • 退出先完成撤销：退出侧清空 runner → 检查时没有在途投递 → 取消侧才登记 → 取消侧读到 null。它没有可中断的旧 runner。

关键是两个 volatile 字段上的读写顺序。不能把“投递中”移到读取 runner 之后，也不能把退出等待移到清空 runner 之前。

正式落地时的边界

  • 这个布尔标志依赖 AbstractFuture 对一次成功 cancel(true) 只调用一次 interruptTask()；若以后支持多个独立投递者，必须改用能协调多投递者的协议。
  • 投递结束必须在 finally 中发布，包括 interrupt() 抛异常时。等待不能被取消中断提前打断。
  • 只等待中断投递完成，不等待 A 的任务体配合取消。自定义 interrupt() 若永久阻塞，安全退出也会被阻塞；不能用超时放行来重新引入越界。
  • 应补充取消早于 runner 发布、cancel(false)、inline、入口标志恢复、投递异常和正常完成竞争的测试。当前 Java 8 探针不是完整回归验收；本轮未独立复核 JDK 25。
