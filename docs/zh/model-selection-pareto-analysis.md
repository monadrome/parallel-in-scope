# 模型选择：价格、能力与帕累托集合分析

> 本文整理一次模型选择讨论的结论。数据检索日期为 2026-08-25；模型可用性和费用倍率应以运行 `ada model` 的当日结果为准。

## 1. 问题与候选集

目标是在当前可用模型中寻找“成本更低、能力更强”的候选，而不是仅按能力或价格排序。

候选来自 `ada model`。模型的公开能力数据来自 [Artificial Analysis Models](https://artificialanalysis.ai/models)。有两种能力口径：

| 口径 | Artificial Analysis 指标 | 含义 |
| --- | --- | --- |
| 综合能力 | Intelligence Index v4.1.1 | 九项评测的综合指标，含 Terminal-Bench v2.1、SciCode 等 |
| 编程 / Agent 能力 | Terminal-Bench v2.1 | Agentic coding 与 terminal use，更贴近带工具的编程任务 |

本次最终采用“综合能力 + 费用倍率”的二维口径。

## 2. 帕累托支配的定义

将费用倍率记为 `cost`（越小越好），综合评分记为 `score`（越大越好）。模型 A 支配模型 B，当且仅当：

```text
A.cost <= B.cost
且 A.score >= B.score
且至少一个不等式严格成立
```

没有被任何候选支配的模型组成帕累托集合（Pareto frontier）。它们不是“同样好”，而是分别代表不同成本档位上的最佳能力边界。

## 3. 为什么本次只采用费用倍率

最初曾按输入和输出 token 单价作为两个独立成本目标。这种做法适合输入 / 输出比例未知且希望严格保留所有成本偏好的场景，但与本次提供的“费用倍率”口径不一致。

费用倍率已经是平台折算后的单一综合价格，因此本次改用：

```text
目标 1：费用倍率最小化
目标 2：Intelligence Index 最大化
```

这会把三维 Skyline 问题化简为二维前沿问题。

## 4. 综合能力帕累托集合

按费用倍率从低到高排序。以下是当时可复核公开评分、且位于二维前沿的模型：

| 模型 | 费用倍率 | Intelligence Index | 选择意义 |
| --- | ---: | ---: | --- |
| MiniMax-M3 | 0.31X | 45.40 | 最低的公开可验证高能力档 |
| DeepSeek-V4-Flash / Flash-0731 | 0.32X | 51.77 | 仅略增成本，但综合能力明显提升 |
| GLM-5.2-discount | 0.77X | 52.64 | Flash 之后的低成本小幅升级 |
| DeepSeek-V4-Pro-discount | 0.95X | 53.20 | 进一步提升综合能力 |
| Qwen3.8-Max | 1.04X | 58.08 | 中价位的显著能力跃迁 |
| Kimi-K3 | 1.68X | 59.70 | 更高能力档 |
| GPT-5.6 Sol | 5.15X | 60.93 | 公开综合评分最高的在列点，成本也最高 |

`DeepSeek-V4-Flash` 与 `DeepSeek-V4-Flash-0731` 公开底模评分、当时费用倍率均相同，可视为同一前沿点。

### 被排除的典型原因

- MiniMax-M2.7、Qwen3.6-Plus、Qwen3.7-Plus：被 MiniMax-M3 以更低或相近倍率和更高综合分支配。
- GLM-5.1、Kimi-K2.6、Kimi-K2.7-Code、Qwen3.7-Max：在更低倍率处已经存在综合分更高的模型。
- Claude Sonnet / Opus：在本次费用倍率口径下，有更低倍率且综合分更高的前沿模型。
- GPT-5.4、GPT-5.5、GPT-5.6 Luna、GPT-5.6 Terra：其综合分没有在对应费用倍率处创造新的最高值；例如 Terra 的 56.58 低于 Qwen3.8-Max 的 58.08，而倍率更高。

## 5. 编程能力口径的前沿（参考）

若目标改为 Terminal-Bench v2.1，则结果不同：

| 模型 | 费用倍率 | Terminal-Bench v2.1 |
| --- | ---: | ---: |
| MiniMax-M3 | 0.31X | 65.2% |
| DeepSeek-V4-Flash / Flash-0731 | 0.32X | 78.7% |
| GPT-5.6 Luna | 0.85X | 80.9% |
| Qwen3.8-Max | 1.04X | 81.3% |
| Kimi-K3 | 1.68X | 85.0% |
| GPT-5.6 Terra | 2.29X | 88.0% |

这说明综合能力和 coding/agent 能力不应混用：例如某个模型可能不再提升综合分，却能提升 Terminal-Bench。

## 6. DeepSeek-V4-Flash-yun：为何不进入正式集合

`DeepSeek-V4-Flash-yun` 的费用倍率为 0.15X，但该服务是阿里云部署的量化版本；它不是公开评测中 `DeepSeek V4 Flash 0731` 的已验证等价物。

因此不能直接复用原版的 Intelligence Index 51.77 或 Terminal-Bench 78.7%。正式帕累托计算中暂将其排除，避免“低价量化版本被误当成原版能力”而错误支配其他模型。

### 量化影响的经验结论

| 量化类别 | 通常经验 | 用于代码 Agent 的建议 |
| --- | --- | --- |
| INT8 | 经正确校准后常接近无损 | 通常可近似原版，但仍需抽样验证 |
| 优质 W4A16 / 4-bit weight-only（AWQ、GPTQ） | 短对话和短代码可能只小幅下降 | 多轮工具调用与长上下文仍需验证 |
| W4A4 或激进 KV-cache 量化 | 长上下文、推理稳定性和格式遵循更容易退化 | 不作为复杂 coding agent 的主模型 |
| 3-bit 及以下 | 降幅和方差通常明显 | 仅用于低风险、可快速验证的任务 |

公开研究支持“经恰当处理的 INT8 / 4-bit 可能在标准基准上接近原模型”，但并不证明它们在 SWE-bench 或 Terminal-Bench 这类多步 agent 任务中等价：

- [LLM.int8()](https://arxiv.org/abs/2208.07339)
- [SmoothQuant](https://arxiv.org/abs/2211.10438)
- [GPTQ](https://arxiv.org/abs/2210.17323)
- [AWQ](https://arxiv.org/abs/2306.00978)

Agent 任务会放大每一步的小误差。例如六次关键决策中，单步正确率由 90% 降至 87%，全链成功率会由 `0.9^6 = 53%` 降至 `0.87^6 = 43%`。

### 对 yun 版本的暂定策略

- 用于小函数、局部改动、格式转换、简单测试补齐和可快速运行验证的任务。
- 遇到多文件改动、复杂调试、长链路工具调用或关键上线变更，升级到原版 Flash 或更高档模型。
- 不使用未经验证的估计分数参与正式帕累托集合。

最小验证方案：在相同 prompt、温度、工具链下，对原版 Flash 与 `-yun` 各运行约 20 个单函数修复和 20 个多文件缺陷修复，以测试通过率、首轮成功率和平均迭代数比较。若 `-yun` 达到原版对应指标的 90% 以上，才可将其纳入低成本候选；否则只保留为低风险路由。

## 7. 二维前沿的计算方法

本次为二维问题，最简单高效的算法是排序扫描：

```text
按 cost 升序排序；同 cost 时按 score 降序排序
bestScore = -∞
for point in points:
  if point.score > bestScore:
    输出 point
    bestScore = point.score
```

时间复杂度为排序的 `O(n log n)`，扫描为 `O(n)`；总计 `O(n log n)`，额外空间为 `O(1)`（不计排序与输出）。同费用倍率但分数较低的点会自然被跳过。

若改回输入价、输出价、能力三项目标，不能使用该扫描算法，需采用两两支配比较 / Skyline / 分治算法。一次支配比较是 `O(m)`，朴素做法在 `n` 个候选、`m` 个目标下为 `O(n²m)`。

## 8. 多目标（m > 3）时的算法取舍

| 方法 | 首层前沿复杂度 | 特点 |
| --- | ---: | --- |
| 两两比较 / 朴素 Skyline | `O(n²m)` | 稳妥，适合中小数据和任意目标数 |
| NSGA-II 非支配排序 | `O(n²m)` | 可计算所有非支配层，常用于优化算法 |
| 固定维度分治 maxima | 约 `O(n log^(m-2) n)` | 只求首层时有效；维数升高后优势下降 |
| K-d tree / R-tree Skyline | 平均情况较好，最坏 `O(n²m)` | 适合已有索引的在线查询，低/中维更有效 |
| 增量维护 | 单次插入 `O(|F|m)` | 适合候选不断加入，`F` 为当前前沿规模 |

高维存在“维度灾难”：目标越多，随机点之间越难相互支配，前沿可能包含大部分点。实践中通常先删除高度相关指标、设置硬约束，或采用 epsilon-dominance / 加权效用函数把过大的前沿压缩为可决策的候选集。

## 9. 使用建议

1. 以任务类型先选能力口径：工程 / Agent 编程优先看 Terminal-Bench；综合知识工作优先看 Intelligence Index。
2. 以费用倍率作为默认综合成本，但若任务输入输出比例极端，再回退到输入、输出价格的多目标口径。
3. 帕累托集合用于缩小选择范围；最终路由还应加入上下文长度、图像/视频能力、可用性、延迟、稳定性和实际任务成功率。
4. 对内部、量化、折扣或云托管变体，建立自己的对照基准，避免用公开原版成绩做无依据映射。
