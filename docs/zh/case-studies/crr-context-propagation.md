# 不想把上下文传播绑死在 TTL 上，我们改了什么？

一次请求进入系统后，往往会带着一些“随身信息”：请求编号、日志字段、当前租户，或者链路追踪信息。业务代码不想把这些参数层层传下去，于是把它们放在线程上下文里。

问题出现在任务被交给线程池之后：**任务换了线程，这些信息该怎么跟过去？任务结束后，又该怎么不留痕迹地离开？**

`parallel-in-scope` 原来主要通过 Alibaba TransmittableThreadLocal，简称 TTL，处理这件事。这次改动不是把 TTL 换成另一个库，而是把它背后的工作拆开，让 TTL 成为默认实现，而不再是应用上下文传播的唯一选择。

本文说明这次已经写进代码的改动，以及为什么这样改。内容对应 `0.5.0-SNAPSHOT` 开发线上的 CRR 实现，不是已经发布到稳定版 `0.4.1` 的功能说明。更广范围的变异测试审计尚未完成，因此也不能把本文理解为“生产验收已经全部通过”。

## 问题一：不用 TTL，就一定要自己包装每个任务吗？

假设你的系统已经有自己的请求上下文。如果并发库只认识 TTL，就容易出现两种选择：

- 为了使用并发库，再把同一份信息接入 TTL。
- 在每个任务周围手写保存、安装、清理逻辑。

后一种方式大致长这样。这里的 `RequestSnapshot` 和 `RequestScope` 是应用自己提供的类型：

```java
RequestSnapshot captured = requestContext.capture();
par.map(orderIds, orderId -> {
    try (RequestScope scope = captured.install()) {
        return loadQuote(orderId);
    }
}, options);
```

真正的问题不是多写几行，而是每个调用点都要回答同一组问题：在哪里捕获？什么时候恢复？异常时谁负责清理？回调晚一点执行时，还能拿到正确的请求信息吗？

这次我们增加了 `ContextPropagation`，让应用可以在运行时配置自己的传播方式：

```java
ParRuntime runtime = ParRuntime.builder()
        .register(ParId.of("workers"), pool)
        .contextPropagation(requestContext)
        .build();
```

这里的 `requestContext` 实现新的 `ContextPropagation` 接口。配置完成后，任务不必再重复包装自己的上下文。

这个变化的收益是：**业务继续使用熟悉的上下文系统，并发库统一处理捕获时机和清理边界。**上面的代码只展示配置；实际使用中，仍应通过 try-with-resources 关闭运行时，并由线程池的所有者管理线程池生命周期。

## 问题二：CRR 到底是什么，为什么看起来又像一个栈？

CRR 是三个动作的缩写：

| 动作 | 通俗解释 | 请求编号的例子 |
|---|---|---|
| Capture，捕获 | 记下任务应该携带什么 | 记下当前请求编号是 `order-1024` |
| Replay，安装 | 执行任务前，把信息放到执行线程上 | 让任务读取到 `order-1024` |
| Restore，恢复 | 任务结束后，恢复执行线程原来的状态 | 还原工作线程之前的请求编号，或者移除绑定 |

它不是网络通信协议，也不负责跨进程传输。这里说的“协议”，是不同上下文实现与并发库之间共同遵守的规则。

代码里把这组规则分成了三个角色：

- `ContextPropagation`：负责捕获。
- `ContextSnapshot`：保存捕获结果，可以被重复使用，也可以跨线程安装。
- `ContextScope`：代表某一次具体安装，负责在结束时恢复。

为什么还需要一个栈？因为执行可以嵌套。比如外层任务安装了请求 A，内层任务临时安装请求 B，退出内层时应该回到 A，而不是直接清空。

```text
线程原来的状态
  → 安装请求 A
    → 安装请求 B
    → 退出 B，恢复 A
  → 退出 A，恢复线程原来的状态
```

所以，**栈负责管理安装的先后顺序，CRR 还负责捕获、复用、失败处理和任务生命周期。它不只是一个栈。**

这里特别区分了“快照”和“安装”。同一份快照可以供多个任务使用，但每次安装都会获得独立的 scope。库会拒绝在另一条线程上关闭 scope，也会拒绝先关外层、后关内层；被拒绝的关闭不会先去修改上下文。

这只能保证绑定的恢复，不能保证任意对象的深拷贝。如果快照里放的是一个可变 Map，并且多个任务共享同一个 Map，恢复绑定并不会撤销对 Map 内容的修改。是否复制数据，仍是上下文提供者的责任。

## 问题三：哪些东西可以替换，哪些绝对不能一起关掉？

请求编号和租户信息属于应用。但“这是哪个任务”“父任务是否取消”“截止时间是什么”属于并发库自身。

这两类信息如果混在同一个可替换机制里，就会出现危险的配置含义：用户只是想关闭日志上下文传播，却连取消或者任务识别也一起关掉了。

这次改动把边界明确分开：

| 内容 | 谁负责 | 是否由应用提供者替换 |
|---|---|---|
| 请求编号、日志字段、应用已有的追踪上下文 | 应用的 `ContextPropagation` | 可以 |
| 任务身份、取消关系、截止时间 | 并发库 | 不可以 |
| 提交任务时使用的内部策略上下文 | 并发库 | 不可以 |

因此，现在可以明确选择不传播应用上下文：

```java
ParRuntime runtime = ParRuntime.builder()
        .register(ParId.of("workers"), pool)
        .contextPropagation(ContextPropagation.none())
        .build();
```

`none()` 的含义是“不替你搬运应用上下文”，不是“清空工作线程上的所有上下文”，也不是“关闭取消与超时”。如果外部线程池或代理已经安装了自己的 TTL 包装，选择 `none()` 也不会替你拆掉那个包装。

这条无操作路径还做了一个小优化：重复捕获复用同一份不可变的空快照，不再为每次捕获创建新的快照对象。不过，每次安装的 scope 仍然独立，不能为了省对象而共享关闭状态。这里没有据此宣称吞吐量提升了多少；那需要另做基准测试。

## 问题四：上下文应该在提交时捕获，还是执行时捕获？

假设请求 A 创建了三个子任务，但线程池暂时只能运行其中一个。后两个任务可能过一会儿才获得执行机会。

如果等到真正交给工作线程时才捕获，捕获到的可能是别的任务完成时留下的上下文，而不是请求 A。

所以，这次改动保留并统一了一个关键规则：**任务在准备阶段捕获上下文，不等到获得执行机会之后再捕获。**

这条规则不仅用于单个任务，还用于批量任务、等待空闲并发名额的任务，以及在前面结果齐全后才运行的汇总任务。它们可以晚一点执行，但不能因此换一份请求身份。

回调则需要区分两个问题：

| 你希望回调使用什么上下文 | 对应入口 |
|---|---|
| 谁现在调用 `execute`，就使用谁的上下文 | `ContextExecutors.directContextExecutor(provider)` |
| 使用当初注册这个回调时的上下文 | `ContextExecutors.registrationContextExecutor(provider)` |

例如，请求 A 注册了一个 Future 监听器，最后却由请求 B 所在的线程触发执行。如果监听器属于 A，就应该选择注册时捕获，而不是把 B 的身份带进去。

这两个 helper 都在调用它们的线程上直接执行回调，并不会额外创建线程。注册时捕获的 helper 会保留那份快照，因此也不应该把同一个实例当作全局对象，供互不相关的请求共享。

## 问题五：捕获失败了，之前准备好的任务怎么办？

这是最容易被“正常路径能跑通”掩盖的问题。

假设一个批次有三个任务：第一个任务已经捕获成功，第二个任务的上下文提供者却抛出了异常。如果此时第一个任务已经提交出去，调用者会遇到一个很难处理的状态：接口报错了，但部分业务可能已经执行。

这次实现把准备和提交分开：

```text
先准备本次提交需要的任务，并捕获上下文
  → 全部成功：才开始向线程池提交
  → 任意失败：清理已准备的任务，然后把原异常交给调用者
```

这一点也覆盖了汇总任务：不能因为元素任务已经准备好，就忽略汇总任务捕获失败之后的清理。

进一步验证时，我们确实发现了一个具体遗漏：捕获失败发生在任务 Future 创建之前，而执行槽位已经登记。原来的失败路径取消了任务所属单元，却没有把这个永远不会执行的槽位标记为“不会开始”。

现在，这条路径会同时取消所属单元，并把已登记的执行槽位释放掉。有些内部调用没有登记槽位，也能保留原来的异常，不会因为补清理而产生新的空值错误。

针对这个问题，测试不再只看“业务没有运行”，还检查：

- 之前准备好的 Future 已经取消，并释放了保存的 Callable。
- 已登记的槽位不再处于等待执行状态，计数确实得到释放。
- 取消父子关系中用于保留子任务的引用已经断开。
- 完成观测成功给出了“已取消、没有取得执行资格”的结果，而不只是随便完成了一个异常 Future。
- 外层任务仍然可以继续运行，不会被失败的子任务反向取消。

这些检查发生在关闭整个运行时之前，避免让运行时关闭顺带完成清理，从而掩盖准备阶段本身的遗漏。

对于由调用者交给任务组管理的现有 Future，仍遵守原来的接管规则：在 `runAll()` 转移所有权之后，即使准备失败，相关的未连接来源也要取消。CRR 没有另外发明一套相反的所有权语义。

## 问题六：业务执行完了，为什么还不能马上说任务结束？

任务的最后一行业务代码返回，并不代表工作线程已经干净了。后面可能还要恢复应用上下文、释放捕获对象。

如果过早发布“执行结束”，等待任务结束的一方就可能以为资源已经可以安全回收；完成监听器也可能看到尚未清理完的状态。

因此，这次调整了结束顺序：

```text
业务代码返回或抛异常
  → 恢复应用上下文
  → 释放持有的 Callable
  → 发布物理执行结束
  → 正常完成通知
```

取消仍然可以先让调用者看到取消结果，但这不等于执行线程已经退出。取消结果与物理执行结束，是两件不同的事。

在新的 CRR 包装路径里，如果业务和恢复过程都抛出了异常，恢复错误不能把业务原来的错误盖掉：主异常继续保留，清理错误作为附加异常记录。组合多个提供者时，会按照安装的相反顺序尽量完成清理；某一次清理失败，不应阻止后面的清理尝试。TTL 自身内部处理掉的错误，仍遵循 TTL 的原有行为。

这些规则都留在同一条执行路径里，而不是为了支持新提供者，另外造一套提交、取消和完成通知机制。

## 问题七：普通 ThreadLocal 怎样接入？

下面用一个不可变字符串说明提供者要做什么。它不是内置的请求上下文组件，只是应用接入的最小例子：

```java
ThreadLocal<String> requestId = new ThreadLocal<>();

ContextPropagation requests = () -> {
    String captured = requestId.get();
    return ContextSnapshot.of(() -> {
        String previous = requestId.get();
        if (captured == null) {
            requestId.remove();
        } else {
            requestId.set(captured);
        }
        return () -> {
            if (previous == null) {
                requestId.remove();
            } else {
                requestId.set(previous);
            }
        };
    });
};
```

随后把 `requests` 传给运行时的 `contextPropagation(...)` 即可。提供者负责知道“怎样读取和恢复自己的数据”；库负责何时调用它，以及任务退出时如何收尾。

如果应用有两套互不重叠的上下文，可以用 `ContextPropagation.compose(...)` 按顺序组合。前提是它们确实管理不同的绑定；库不会自动解决两个提供者同时修改同一份状态的冲突。

提供者还有几个不能省略的责任：捕获应能并发调用，不能偷偷修改调用线程的绑定，也不能先占用必须显式释放的资源，因为任务可能在安装前就被取消；快照应能重复和跨线程安装；安装失败时，提供者应自行撤销尚未交出恢复动作的局部修改。库无法恢复它不知道如何恢复的外部状态。

## 最后：这次没有做什么？

没有移除 TTL 依赖，没有拆出新的发布模块，也没有要求现有 TTL 用户修改配置。默认任务路径仍保留既有的 TTL Callable 包装方式，避免为了提供可替换性而改变原有复制与增强识别行为。

也没有把所有问题都包装成“已经验证完成”。当前分支的完整测试套件已经通过，针对捕获失败补充的回归测试也通过；撤回槽位清理修复后，四个相关用例会失败，说明断言确实能发现这个遗漏。与此同时，更广范围的生命周期和提交机制变异测试还存在存活、未覆盖和超时条目，需要继续逐项分析，不能把 Maven 命令成功退出当成这些条目全部通过。

这次改动最重要的并不是多了三个类型，而是明确了一个边界：**应用决定要携带什么，并发库负责在正确的时机搬过去，并在正确的边界收回来。TTL 可以是默认答案，但不再是唯一答案。**
