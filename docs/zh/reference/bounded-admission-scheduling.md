# 准入机制：滑动窗口怎样控制任务提交

当前项目用滑动窗口控制批量任务进入线程池的速度。窗口里的任务已经提交，可能正在运行，也可能在队列中等待；窗口外的任务还没有提交。

假设一次批量任务有 100 个元素，并且并发度设置为 8。调度器不会一开始就把 100 个任务全部提交给线程池，而是先提交前 8 个任务。每当其中一个任务完成，窗口就向前移动，再提交下一个任务。于是，系统始终只维持一个大小受控的“在途任务窗口”。

```text
提交前 8 个任务

任务完成一个
    ↓
释放一个并发位置
    ↓
提交下一个尚未提交的任务
    ↓
继续等待完成
```

这个做法和 TCP 的滑动窗口有点像。TCP 会限制尚未确认的数据量，收到确认后才继续发送；这里则是在任务完成后补交新的任务。

这里的准入控制很直接：任务创建后不会自动进入线程池，必须等窗口出现空位。这个边界同时决定提交时机、在途任务数量，以及失败或取消后哪些任务可以不再提交。

这和普通的线程池队列有明显区别。线程池通常允许调用方不断提交任务，然后把任务放入工作队列。这样做简单，但当任务数量很多时，队列会迅速膨胀；如果任务本身还会同步等待其他任务，就可能形成线程池饥饿。

滑动窗口把“提交任务”和“执行任务”分开了。尚未进入窗口的任务还没有提交给线程池，因此它们不会占用工作队列，也不会消耗线程池资源。这带来几个直接好处：

- 限制实际在途任务数量，控制内存和队列压力；
- 失败时可以取消尚未提交的任务；
- 超时或父任务取消时，可以减少无意义的任务提交；
- 任务组的生命周期更加清晰；
- 不需要让大量线程阻塞在等待并发许可上。

所以，`parallelism` 控制的是提交节奏，而不只是运行中的线程数。窗口有空位时，调度器才会继续提交。

这也是它和信号量方案的主要区别。信号量通常是先把任务提交给线程池，再在任务内部执行：

```java
executor.submit(() -> {
    semaphore.acquire();
    try {
        executeTask();
    } finally {
        semaphore.release();
    }
});
```

这种方式限制的是任务真正执行的数量，但任务已经进入线程池或工作队列。工作线程可能只是等信号量，既占着线程，也没有处理业务。

滑动窗口则在提交之前做决定：窗口有空位时提交任务，窗口已满时暂不提交，任务完成后再补充提交。信号量更适合限制共享资源，例如数据库连接、外部接口额度或文件句柄；滑动窗口更适合限制一批任务进入执行系统的速度和数量。前者控制资源使用，后者控制任务流入。

当前项目把准入控制放进了结构化并发的生命周期里。任务提交前就已经创建任务视图并绑定取消关系，因此窗口外的任务也能响应父任务取消、批次失败和 deadline。

这和只给已提交任务创建句柄的延迟提交方案不同。每个任务从创建开始就有可观测、可取消的视图；滑动窗口只决定它何时进入线程池。

可以从五个角度看这个机制：

1. 从算法看，它是滑动窗口调度。
2. 从系统控制看，它是准入控制和背压。
3. 从调度策略看，它是按完成事件驱动的需求调度。
4. 从并发模型看，它是结构化并发中的有界扇出。
5. 从资源管理看，任务提交、执行、取消和回收属于同一个生命周期。

它和响应式流中的背压也有相似之处：下游处理能力有限时，上游不能无限制地产生工作。不过当前项目的对象是一次任务批次，而不是持续的数据流，因此更准确的说法是“批次级背压”或“基于滑动窗口的结构化并发准入控制”。

失败时也一样。假设第 3 个任务失败，系统会取消已经提交但尚未完成的任务，并停止补交窗口外的任务。那些任务从未进入线程池，不需要再从队列中清理。

因此，这套机制可以叫作“基于滑动窗口的结构化并发准入控制”：窗口限制任务流入，完成事件推动下一次提交，取消、失败和 deadline 贯穿整个批次。
