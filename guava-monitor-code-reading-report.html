Guava Monitor：把条件等待变成可组合的并发协议

Monitor 不是一种新锁，而是建立在 ReentrantLock 之上的条件协调器。 它最有价值的地方，是让业务代码只声明“什么时候允许继续”，并由框架处理等待循环、等待者登记、 超时、中断和选择性唤醒。本文以 Guava 33.6.0-jre 和项目中的可伸缩阻塞队列为证据。

Java 8+ Guava 33.6.0-jre Monitor / Guard 2026-08-04

Summary

一句话：Monitor = ReentrantLock + 每个 Guard 一个 Condition + 自动 while 重检 + 隐式、按谓词选择的 signal。 它非常适合“一个共享状态、多个等待条件、状态变化路径很多”的组件。它减少的是协议错误和维护成本， 不是锁竞争本身，也不会替你设计正确的状态边界。

Business Goal

问题

传统条件变量要求开发者在每个状态修改点正确选择 signal 或 signalAll，并在等待端手写循环、超时和中断处理。遗漏任意一处都可能永久挂起。

机制

把“可继续条件”封装为 Guard.isSatisfied()。线程离开监视器时，Monitor 检查活跃 Guard，只唤醒一个当前已经满足的等待者。

结果

业务方法围绕状态谓词表达，例如“队列非空才能取”“队列有容量才能放”，不再散落显式信号和容易写错的等待循环。

Scope

  • Guava 33.6.0-jre 的 com.google.common.util.concurrent.Monitor 实现。
  • 项目中的 SimpleResizableBlockingQueueV2，以及手写锁协议的 V1 版本。
  • 重点覆盖等待、隐式唤醒、超时、中断、公平性和适用边界；不展开所有观测型 API。

Business Terms

术语直白解释这里为什么重要
Monitor可重入互斥锁及其条件协调规则的封装。保证同一时刻只有一个线程修改受保护状态。
Guard一个无副作用的布尔谓词，例如“队列非空”。线程不是等待某个信号，而是等待这个事实变成真。
隐式唤醒业务代码不调用 signal()；离开 Monitor 时由框架检查并唤醒。状态更新路径增加时，不必记得同步补信号。
活跃 Guard当前至少有一个线程正在等待的 Guard。Monitor 只扫描这些 Guard，避免检查所有已定义谓词。
信号传递获得唤醒责任的线程在退出或转入等待时继续唤醒下一个合格者。用于避免中断、多 Condition 和竞争重新获取锁时丢失信号。

02

03

检查谓词

条件为假则登记等待者，并在对应 Condition 上等待。

04

条件为真时，调用方持锁继续执行临界区。

05

Pseudocode Walkthrough

主路径：等待条件后进入

enterWhen(guard):
  verify guard belongs to this monitor
  acquire reentrant lock interruptibly
  if guard is false:
    register guard as active
    do:
      await guard's Condition
    while guard is still false
    unregister waiter
  return while still holding the lock

leave():
  if this is the outermost leave:
    scan active guards
    signal the first satisfied guard
  unlock

调用方从 enterWhen 返回时同时拥有两个保证：锁已经持有，Guard 当前为真。因此后续状态操作可以直接执行；但仍必须在 finally 中调用 leave()。

Execution Flow

  1. Guard 构造时创建一个专属 Condition；每个 Guard 记录自己的等待线程数。
  2. 首个等待者到来时，Guard 被挂入 activeGuards 单链表；最后一个等待者离开时再摘除。
  3. await() 使用 do/while 重检谓词，正确覆盖虚假唤醒和条件被其他线程再次改假的情况。
  4. 最外层 leave() 扫描活跃 Guard，找到第一个已满足者后仅调用一次 signal()。
  5. 如果 Guard 计算抛异常，内部会先 signalAll 所有等待者再继续抛出，避免其余线程被永久遗留。

Key Code Anchors

1. Guard 是绑定 Monitor 的谓词和独立 Condition

public abstract static class Guard {
  final Monitor monitor;
  final Condition condition;
  int waiterCount = 0;
  Guard next;

  protected Guard(Monitor monitor) {
    this.monitor = checkNotNull(monitor, "monitor");
    this.condition = monitor.lock.newCondition();
  }

  public abstract boolean isSatisfied();
}

这说明 Monitor 没有消灭 Condition，而是为每个业务条件自动管理一个 Condition，并将其生命周期与谓词绑定。

Monitor.java:296，Guava 33.6.0-jre source jar

2. 隐式唤醒只选择一个已经满足的 Guard

private void signalNextWaiter() {
  for (Guard guard = activeGuards; guard != null; guard = guard.next) {
    if (isSatisfied(guard)) {
      guard.condition.signal();
      break;
    }
  }
}

与无差别 signalAll() 不同，它先用业务谓词筛选，再只唤醒一个线程。这是 Monitor 最核心的“按条件路由信号”能力。

Monitor.java:1067，Guava 33.6.0-jre source jar

3. 等待循环和等待者登记由框架统一实现

beginWaitingFor(guard);
try {
  do {
    guard.condition.await();
  } while (!guard.isSatisfied());
} finally {
  endWaitingFor(guard);
}

正确的 while 重检不再依赖每个业务方法都记住；等待者即使中断或异常退出，也会在 finally 中注销。

Monitor.java:1173，Guava 33.6.0-jre source jar

项目实例：可伸缩阻塞队列

该队列的困难不只是“满时等待、空时等待”，还在于 resize() 会替换底层队列。已经阻塞的线程醒来后必须重新读取新 delegate，而不能继续等待旧队列自己的 Condition。

V2 用两个 Guard 表达许可条件

private final Monitor monitor = new Monitor(true);
private final Monitor.Guard notEmpty = monitor.newGuard(this::canTake);
private final Monitor.Guard notFull = monitor.newGuard(this::hasCapacity);

public void put(E element) throws InterruptedException {
  monitor.enterWhen(notFull);
  try {
    queue().offer(element);
  } finally {
    monitor.leave();
  }
}

resize()、take()、put() 和普通状态修改都经过同一个 Monitor。替换队列后不需要显式广播；离开时新状态会被 Guard 重新判断。

关注点V1：手写 ReentrantLock / ConditionV2：Monitor
条件定义notEmpty、notFull Condition，加独立状态检查方法。notEmpty、notFull Guard 直接绑定谓词。
等待循环四个 await* 方法分别手写 while 和超时更新。enterWhen 及其 timed 版本统一处理。
唤醒每个修改点调用正确的 signalNotEmpty、signalNotFull 或 signalAll。最外层 leave() 自动评估活跃 Guard。
等待者 bookkeeping两个 AtomicInteger 计数器手工维护。Guard.waiterCount 和 activeGuards 内部维护。
并发度生命周期读锁允许底层 enqueue/dequeue 保留更多并发。所有短队列操作经过单个 Monitor，协议更强但更串行。
额外锁读写锁 + 等待锁。仍保留 drainLock，说明 Monitor 不能消除领域特有的跨回调约束。
V2 更容易证明“不会漏信号”，但不必然吞吐更高。这里是典型的可维护性换取更粗粒度串行化；是否值得，需要用真实负载基准判断。

API 选择地图

API锁忙时Guard 为假时中断语义典型用途
enter()一直等不涉及 Guard获取锁阶段不可中断普通临界区
enterInterruptibly()一直等不涉及 Guard可中断需要取消的普通临界区
tryEnter()立即失败不涉及 Guard无等待快速探测；忽略公平设置
enterWhen(g)等待继续等待到为真可中断阻塞队列 put/take
enterWhen(g, timeout)计入总超时计入同一总超时可中断有截止时间的条件进入
enterIf(g)等待获得锁立即释放锁并返回 false普通版不可中断原子检查并执行，不等待状态变化
tryEnterIf(g)立即失败立即失败无等待完全非阻塞探测
waitFor(g)调用前已经持锁释放锁并等待可中断临界区执行到一半，需要等待另一个阶段

所有返回 true 或 void 成功返回的 enter 系列方法，都会让当前线程继续持有 Monitor；调用方负责 leave()。

Risks and Unknowns

  • Guard 必须纯且便宜。Guava 可能在任意持锁线程中检查它；如果 Guard 做 I/O、阻塞、修改状态或抛异常，会把整个 Monitor 的进展绑在谓词上。
  • Guard 依赖的状态必须由同一 Monitor 保护。否则即使字段是可见的，也可能出现“状态改变了，但没有线程经过 leave 触发评估”的协议断裂。
  • 公平锁不等于 Guard 间公平。new Monitor(true) 使用公平 ReentrantLock，但活跃 Guard 是链表，唤醒策略是“第一个满足者”，不是跨业务条件的严格 FIFO。
  • 隐式信号仍有扫描成本。每次最外层离开最多扫描活跃 Guard；Guard 数量多或谓词昂贵时，成本会进入所有写路径。
  • 它是 Guava 绑定。现代 JDK 没有等价标准 API。基础设施若追求零第三方依赖，需要权衡维护手写 Condition 协议的成本。
  • 不要误解为 Actor 或 STM。它仍是共享内存、互斥锁模型；临界区过长、锁顺序错误和外部回调阻塞仍会造成性能或死锁问题。
项目 V2 的 drainTo 特意在调用外部 target.add() 时释放 Monitor，并用额外 drainLock 与 draining 维持队头保留语义。这正说明：Monitor 能简化条件等待，但跨锁外副作用的一致性仍需领域设计。

什么时候值得用

适合

  • 一个对象维护一组明确状态，多个操作等待不同谓词。
  • 状态会从许多方法变化，显式 signal 容易漏。
  • 正确性和可审查性比极致并发度更重要。
  • 需要同时覆盖 interruptible、uninterruptible 和 timed wait。

不优先

  • 只有一个简单互斥区，用 synchronized 已足够。
  • 已有成熟并发容器、Semaphore、CountDownLatch 或 Phaser 能直接表达问题。
  • 需要读写并发、分段锁或无锁算法的吞吐。
  • Guard 数量巨大、谓词昂贵，或状态不属于同一锁边界。

对本项目的判断：V2 是展示 Monitor 优势的好案例。它比 V1 更短、更难漏唤醒，也更容易审查；代价是队列短操作统一串行化。若此队列处于高吞吐热点，应以基准测试决定 V1/V2，而不是仅凭代码行数选择。
