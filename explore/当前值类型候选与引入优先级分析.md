# 当前值类型候选与引入优先级分析

## 背景与目标

本文盘点当前代码中由 `String`、`int`、`long` 和 `double` 承载的领域含义，判断哪些地方值得引入值类型，哪些地方应继续使用 JDK 原生类型。

评估不以“消灭所有 primitive”为目标，而是遵循 `design/first-principles.md` 的顺序：

1. 值类型能消除哪类可具体说明的误用；
2. 现有类型或参数化机制是否已经解决了该问题；
3. 新类型是否澄清了 identity、label、duration 和 deadline 等不同语义；
4. 对公共 API 的仪式感和迁移成本是否低于其安全收益；
5. 是否仍然贴近 Java 8 和 JDK 并发 API 的用法。

## 先区分三类对象

### 值类型

值类型通常不可变，按领域值比较，并在构造时保护不变量。例如逻辑 `Par` 查找键和单调时钟 deadline。

### 令牌或句柄

`TaskKey<T>` 不只是 member name 的包装；它还捕获结果类型，并用于取回对应 future。它是类型化键，不应再用一个公共 `MemberName` 取代。

### 有生命周期的实体或状态容器

`CancellationToken`、`TaskGroup`、`MultiTaskContext` 会随执行过程改变或持有特定生命周期状态，不是值类型。不应仅因为它们是小类就按 value object 设计。

## 当前已有的有效类型

| 类型 | 当前作用 | 判断 |
|---|---|---|
| `ExecutorIdentity` | 按 supplied `ExecutorService` 引用判断真实物理资源 | 保留；是正确的 identity 建模 |
| `TaskKey<T>` | 组内成员键 + 结果类型令牌 | 保留；已消除强转和大部分名称查找错误 |
| `Duration` | 相对时长 | 保留；不要退化为 `long + TimeUnit` |
| `TaskType` | CPU/IO 工作负载分类 | 保留 enum |
| `TaskOutcome` | 统一的执行结果词汇 | 保留 enum |
| `ExecutionPhase` | future 执行阶段状态机 | 保留 enum |
| `BlockingRisk` | executor 阻塞风险能力 | 保留 enum |
| `MultiTaskOptions`、`GlobalPar*Policy` | 不可变配置 | 已是聚合值对象，应改进其内部字段而非再套一层 |
| `TaskCompletion`、`TaskGroupResult` | 完成后的不可变数据快照 | 已具有值对象的不可变数据形状；可继续收紧内部非法字段组合 |

`TaskBatchResult` 不在此列：它包装仍在变化的 futures 和 cancellation 能力，是运行句柄，不是按字段值比较的完成快照。

`ExecutorIdentity` 的文本形式仅用于诊断，不能持久化或作为图 key，见 `src/main/java/io/github/monadrome/parallelinscope/scope/ExecutorIdentity.java:7`。

## 候选结论总表

| 候选 | 优先级 | 推荐形态 | 主要消除的错误 |
|---|---:|---|---|
| `ParName` / `ParKey` | P0 | 公共值类型 | 逻辑 `Par` 键与 task/group/label 字符串混用；各入口校验不一致；不保证已在某个 topology 注册 |
| `Deadline` | P0 | 内核值类型，公共边界仍用 `Duration` | 绝对单调时间点、相对时长和无限哨兵值混用；溢出/剩余时间误算 |
| `TaskNode` | P1 | 内部观测值对象 | `parentId/parentLabel/childId/childLabel` 的位置性混淆；`"root"` 哨兵值冲突 |
| `ExecutionEndpoint` | P1 | 内部观测值对象 | executor identity 与其 `Par` label 配对错误 |
| `TaskTiming` | P1 | 完成快照的嵌套值对象 | submit/start/end 三个 `long` 换位和“未开始用 0 表示”的非法组合 |
| `ConcurrencyLimit` | P2 | 先改显式 API；重用增多后再提取类型 | `parallelism <= 0` 同时表示默认/全量并发的魔法数 |
| `Fraction` / `Ratio` | P3 | 仅在第三个使用方出现后引入 | `double` 范围校验分散 |

## P0：`ParName` / `ParKey`

### 当前问题

`GlobalPar` 使用多个 `Map<String, ...>` 保存 `Par`、runtime 和 listener override，同一个字符串语义穿过：

- `GlobalPar.Builder.register(String, ExecutorService)`；
- `defaultPar(String)`；
- `parTaskListener(String, ...)`；
- `GlobalPar.par(String)` / `find(String)`；
- `TaskGroupDefinition.Builder.task(..., String executorName, ...)`；
- terminal combine 的 executor 选择。

见 `GlobalPar.java:51-56, 139-176, 363-435` 与 `TaskGroupDefinition.java:51-117, 144-176`。

现有校验还不完全一致：`register` 和 `parTaskListener` 拒绝 null/空字符串，task-group definition 仅拒绝 null，可以把空 executor name 留到 submit 时才失败。

### 建议语义

```java
public final class ParName {
    private final String value;

    public static ParName of(String value);
    public String value();

    // equals/hashCode 按 value；toString 返回诊断文本
}
```

不变量：

- 非 null；
- `trim()` 后非空；
- 不隐式 trim、lowercase 或其他规范化，避免改变现有 key 语义；
- 按字符串值相等，不按对象引用相等。

### 命名选择

`ParName` 比 `ExecutorId` 更准确。该值选择的是逻辑 `Par` 入口，不是物理 executor；同一个 executor 可以被两个名称不同的 `Par` 共享。物理资源已经由 `ExecutorIdentity` 表示。

如果坚持使用 `ExecutorId`，必须在类文档中明确它是“逻辑注册键”，并且不得出现在 deadlock/purge 的资源 identity 判定中。

### 收益边界

`ParName.of("htpp")` 仍然是格式合法的值；值类型不能证明它已在某个 `GlobalPar` 注册。未注册键仍需在 `build()` 或 `TaskGroup.submit()` 边界拒绝。

对普通 batch 业务代码，比持有 `ParName` 更强的做法仍然是直接注入已绑定的 `Par`。`ParName` 的最大价值在组装根和延迟解析 executor 的 `TaskGroupDefinition`。

### 能否让“引用不存在的 executor”编译失败

单独引入 `ParName` 不能做到。需要分清三种不同保证：

| 保证 | `ParName` 能否提供 | 合适机制 |
|---|---|---|
| 参数是“`Par` 名称”而非其他字符串 | 能 | 名义值类型 + 构造校验 |
| 名称属于当前 `GlobalPar` 的注册集合 | 不能 | topology build/bind/submit 时校验 |
| 物理 executor 此刻未关闭且可接收任务 | 不能 | 提交时状态检查与 rejection 处理 |

第二项是“值是否属于某个运行时对象所持有的集合”。Java 类型系统不能从以下 builder 调用序列中推导出一个新的值级类型：

```java
GlobalPar.builder()
        .register(ParName.of("database"), databaseExecutor)
        .register(ParName.of("http"), httpExecutor)
        .build();
```

Java 8 没有 dependent type/generative type，普通库 API 无法把“这一次 builder 刚好注册了 database 和 http”编码进返回值的静态类型。

#### 枚举能提供什么

库可以用泛型边界强制用户提供 enum：

```java
enum AppPar {
    DATABASE,
    HTTP
}

GlobalPar<AppPar> global = GlobalPar.builder(AppPar.class)
        .register(AppPar.DATABASE, databaseExecutor)
        .register(AppPar.HTTP, httpExecutor)
        .build();
```

Java 在语言上支持这种强制，例如使用 `<E extends Enum<E>>`。它能消除字符串拼写错误，也能阻止 `OtherAppPar` 的键传给 `GlobalPar<AppPar>`。

但 enum 仍不能让“少调了一次 `register`”编译失败。若要确保所有 enum constant 都被注册，`build()` 仍需用 `EnumSet.allOf(AppPar.class)` 做运行时完整性校验。该模式还会：

- 迫使所有用户为库定义一个枚举；
- 让 `GlobalPar`、`TaskGroupDefinition` 及相关 API 全链路携带泛型参数；
- 难以支持来自配置、插件或不同环境的动态 topology；
- 将“某环境不注册某个可选 executor”变得别扭。

因此 enum 是可选的应用层闭集建模，不适合成为该通用库的强制前提。

#### 句柄能提供什么

如果 API 接收由 `GlobalPar` 创建的 `Par` 对象，而非用户自由构造的名称：

```java
Par database = global.par(ParName.of("database"));
definition.task(userRef, database, callable, options);
```

那么 task definition 不会持有一个未解析 executor 键。但这会让 definition 绑定具体 `GlobalPar` 和运行资源，破坏当前“纯数据、可跨 topology 实例复用”的契约。而且 Java 仍无法在编译期阻止把 `globalA` 的 `Par` 传给基于 `globalB` 的 group；需按 owner identity 在运行时检查。

#### 更适合当前架构的折中：未绑定 definition + 已绑定 plan

如果真正目标是“进入业务执行前，executor 引用必须全部有效”，可以用两阶段 typestate，不必强制用户定义 enum：

```java
TaskGroupDefinition definition = TaskGroupDefinition.builder(options)
        .task(userRef, DATABASE, callable, memberOptions)
        .build();

BoundTaskGroupPlan plan = global.bind(definition); // 解析全部 ParName，任一缺失则整体失败
TaskGroup group = TaskGroup.submit(plan);           // 只接受已绑定 plan
```

这里的保证是：

- 实际成员关系在 `bind` 时做运行时校验，因为 topology 本身是运行时对象；
- Java 编译器保证未校验的 `TaskGroupDefinition` 不能直接进入 `submit`；
- bound plan 内部保存真实 `Par`/runtime 句柄，后续不再依赖字符串重新查找；
- 未绑定 definition 仍是纯数据，可以分别绑定到 prod/test 的不同 `GlobalPar` 实例；
- `GlobalPar.close()` 与 executor rejection 仍属于运行时事件，bound plan 不应伪称能在编译期保证资源永远可用。

这不是纯值类型方案：`BoundTaskGroupPlan` 是绑定到具体 topology 生命周期的句柄/plan。但它比试图用 `ParName` 承诺注册表完整性更准确。

#### 当前代码已有的保证

当前 `TaskGroup.buildWhileOpen` 在任何 `submitPrepared()` 之前遍历 definition，通过 `env.par(member.executorName())` 解析所有成员和 combine，见 `TaskGroup.java:450-570`。未知名称会使整个构建失败，已准备的 future 被取消，不会执行部分 callable。

因此当前保证是“submit 边界的原子预检”，而非编译期引用完整性。对动态 topology 来说这是合理基线；只有当拼写错误已在生产路径造成实际成本，才值得增加 bound-plan 概念将失败前移到应用组装期。

## P0：`Deadline`

### 当前问题

`long deadlineNanos` 同时穿过：

- `MultiTaskContext`；
- `CancellationToken`；
- `TaskGroup`；
- `TaskGroupResult`；
- deadline 解析的内部方法。

它不是时长，而是 `System.nanoTime()` 时域上的绝对单调时间点；`Long.MAX_VALUE` 又被用作“无 deadline”。当前代码直接做以下运算：

```java
Math.min(childDeadlineNanos, parentDeadlineNanos)
deadlineNanos - System.nanoTime()
nowNanos + timeoutNanos
```

见 `MultiTaskContext.java:98-157` 和 `CancellationToken.java:46-110, 128-154`。这些运算要求调用者同时记住时域、无限哨兵值、上溢和过期截断规则。

### 建议语义

```java
final class Deadline {
    static Deadline none();
    static Deadline at(long nanoTime);
    static Deadline after(Duration timeout, long nowNanos);

    Deadline earlierThan(Deadline ceiling);
    Duration remaining(long nowNanos);
    boolean expiredAt(long nowNanos);
    long nanoTime(); // 仅供必须的 telemetry/兼容边界
}
```

它应集中保证：

- child deadline 不晚于 parent/group ceiling；
- `Duration` 转换和加法溢出饱和；
- 剩余时间不为负；
- `none()` 的语义不向普通数学运算泄漏；
- 绝不与 wall-clock `Instant` 比较。

公共请求边界仍应使用 `Duration`：用户声明“最多执行多久”，而不应自己构造 `System.nanoTime()` 时域的绝对值。`Deadline` 主要是 scope/cancel 内核类型。

## P1：`TaskNode`

### 当前问题

`TaskGraphObservationScope.logTaskPair` 和 `TaskGraphData.logTaskPair` 接收四个相邻字符串：

```java
(@Nullable String parentId,
 @Nullable String parentLabel,
 String childId,
 @Nullable String childLabel,
 TaskEdge edge)
```

见 `TaskGraphData.java:123-133`。这是典型的位置性 stringly-typed API，且它把 null parent 转换为字面量 `"root"`。理论上，某个 UUID 字符串或外部构造的 child ID 可以与该哨兵值冲突。

### 建议语义

```java
final class TaskNode {
    static TaskNode root();
    static TaskNode unit(String id, @Nullable String label);

    String id();
    @Nullable String label();
}
```

调用面变为：

```java
logTaskPair(@Nullable TaskNode parent, TaskNode child, TaskEdge edge);
```

值对象应明确图节点相等性只由 id 决定，label 是展示属性。如果需要让类型边界更强，可再将 id 提取为 `TaskNodeId`；不建议一开始同时引入两层类型。

`TaskNode` 比只把四个 `String` 分别换成 `UnitId`/`TaskLabel` 更能消除实际错误：它从结构上保证 ID 与 label 成对传递。

第一步可以让 `TaskNode` 仅作为包内记录入口，`TaskGraphData` 再将它投影为现有公共 `ValueGraph<String, ...>`，从而先消除四个位置参数的错误而不扩大 API 变更。只有决定让公共 graph 也按节点类型建模时，`TaskNode` 才需升级为公共类型。

## P1：`ExecutionEndpoint`

### 当前问题

identity-aware `TaskEdge` 构造器分别接收：

```java
ExecutorIdentity executorIdentity,
ExecutorIdentity sourceExecutorIdentity,
String executorName,
String sourceExecutorName
```

见 `TaskEdge.java:79-98`。这保持了资源 identity 与诊断 label 的概念分离，但没有保证每个 identity 与它对应的 label 成对传递。

### 建议语义

```java
final class ExecutionEndpoint {
    private final ExecutorIdentity identity;
    private final ParName parName;
}
```

`TaskEdge` 改为显式的 source/target endpoint：

```java
TaskEdge(
        @Nullable ExecutionEndpoint source,
        ExecutionEndpoint target,
        int parallelism,
        TaskType taskType,
        int taskCount,
        Duration timeout,
        boolean deadlockProne)
```

这不应取代 `ExecutorIdentity`：endpoint 表示一次观测边上的“逻辑入口 + 物理资源”快照，identity 仍是 deadlock/purge 的唯一资源判定依据。

## P1：`TaskTiming`

### 当前问题

`TaskCompletion` 的 factory 连续接收 `submitTimeNanos`、`startTimeNanos`、`endTimeNanos`，见 `TaskCompletion.java:41-122`。未进入用户代码的任务以 `start=0/end=0` 表示，而派生 duration 再将差值截断到零。

当前私有构造器和 factory 已经限制了部分非法状态，所以这不是 P0。但当 timing 继续扩展或需要对外提供更稳定的 telemetry 时，建议聚合为：

```java
final class TaskTiming {
    static TaskTiming completed(long submitted, long started, long ended);
    static TaskTiming neverStarted(long submitted);

    Duration queueWait();
    Duration execution();
    Duration total();
    boolean started();
}
```

该类应校验同一单调时域上的顺序，并隐藏零哨兵细节。不建议分别引入 `SubmitTime`、`StartTime`、`EndTime` 三个小类，因为真实不变量是三者的组合关系。

## P2：`ConcurrencyLimit`

`MultiTaskOptions` 默认保存 `parallelism = -1`，解析时任何非正数都表示“按 task count 全量并发”，见 `MultiTaskOptions.java:71-76, 98-115` 和 `MultiTaskContext.java:124-127`。

主要问题是哨兵值，不是用户会把 parallelism 与另一个 `int` 参数传反。因此建议先改成显式选择：

```java
builder.parallelism(8);       // 只接受正数
builder.allTasksInParallel(); // 显式无局部窗口限制
```

内部可用 enum + 整数或一个私有 `ConcurrencyLimit` 表示。只有当同一概念需要穿过 options、policy 和其他公共 API 时，才值得把它升级为公共值类型。

还应注意，task-group member 根本不读取 parallelism。这更像是 `MultiTaskOptions` 同时服务 Group/Batch 所产生的抽象张力，单独包装 `int` 不会消除该张力。

## P3：`Fraction` / `Ratio`

`GlobalParPurgePolicy` 的两个 `double` threshold 都要求 `(0, 1]`，且已在 builder 的单一 `validate` 方法中校验，见 `GlobalParPurgePolicy.java:36-66`。

当前不建议为此单独引入公共 `Ratio`：

- 校验已集中；
- 两个 builder 方法名已明确表达语义；
- 两个参数即使都变成 `Ratio` 也仍可在业务上设反。

如果后续 rate/ratio 在多个 policy 间共享运算和边界规则，再提取一个包内或公共值类型。

## 当前不建议引入的值类型

### `MemberName`

`TaskKey<T>` 已经把 member name 与结果类型绑定。根据项目的“类型安全下沉到键”原则，业务路径应优先使用 `group.future(key)`，而不是把 `findMember(String)` 换成 `findMember(MemberName)` 后继续使用弱类型查找。

`Map<String, ListenableFuture<?>> members()` 用于异构结果的枚举/诊断，保留字符串 key 是可接受的。

### `TaskName` / `OperationName` / `GroupName`

`MultiTaskOptions.name` 和 group name 主要是诊断 label，已在 options 构造时拒绝空白。它们不参与资源查找、结构化父子关系或相等性判定。

为每次最常用的 `MultiTaskOptions.of("fetch-account")` 强制构造名称值对象，仪式感大于安全收益。只有当 name 从诊断 label 升级为稳定协议键时才需重新评估。

### `GroupId`

group ID 由库内部生成、只在 `TaskGroup` 和完成快照间传递，当前没有按 group ID 接收外部输入或执行查找的 API。包装后主要是名义收益，无法消除高概率错误。

如果未来 group ID 进入跨进程 telemetry、持久化或查询 API，应在该边界引入 `GroupId`。

### `TaskIndex` / `TaskCount`

这些整数在紧凑的任务内核中使用，现有入口已做非负校验。包装会为每个 batch element 增加对象和拆箱成本，而且与 `IntStream.range` / list index 等 JDK 习语对接更繁琐。

应通过更少的位置参数、具名 factory 和聚合对象避免换位，不要为每个数字建类。

### `QueueCapacity`

queue capacity 直接对接 `BlockingQueue.size()`、`remainingCapacity()` 和 `ThreadPoolExecutor` 习语。`SmartBlockingQueue.create(int)` 还故意让非正数表示 `SynchronousQueue`。它属于 JDK 机制参数，不是独立领域标识符。

### checkpoint name 和日志文本

`Checkpoints.checkpoint(String taskName, ...)`、exception message、deadlock event 的 edge 文本均是人类可读诊断数据。它们不应作为查找键，也没有必要值类型化。

`HeuristicPurger.PoolState.executorId` 实际是 `class@identityHash` 格式的日志 label，不是可比较的 executor ID。如果调整命名，更合适的名称是 `executorLabel`，不应因此引入又一个 identity 类型。

### JDK 风格的 timeout 重载

`Checkpoints` 中的 `(long timeout, TimeUnit unit)` 是 JDK 并发 API 的标准形状，同时已对若干操作提供 `Duration` 重载。不应为了类型统一破坏这些 JDK 习语。

## 不应合并的概念

```text
ParName              = 逻辑执行入口的查找键，按字符串值相等
ExecutorIdentity     = supplied executor 的物理资源身份，按引用相等
executor label       = 人类可读的诊断文本

Duration             = 相对时长
Deadline             = 单调时钟上的绝对截止点
wall-clock Instant   = 日历时间，当前执行内核不需要

TaskKey<T>           = 类型化的 group member 键
MultiTaskOptions.name= 执行/监控诊断名称
TaskNode             = 一次具体运行单元在任务图中的身份和 label
```

仅把它们统一命名为 `Id`、`Name` 或 `ExecutionTarget` 会重新制造 ADR 0005 已经拆开的责任混淆。

## 建议实施顺序

### 第一阶段：两个独立高收益改动

1. 引入 `ParName`，一次性贯通 `GlobalPar` 注册/查找/listener override 与 `TaskGroupDefinition` member/combine。
2. 引入内核 `Deadline`，贯通 `MultiTaskContext`、`CancellationToken` 和 `TaskGroup`；对用户仍以 `Duration` 表达 timeout。

两者分开提交，因为一个是 executor topology API 变更，另一个是 cancellation/deadline 内核变更，验证矩阵不同。

### 第二阶段：在观测模块内聚合配对数据

3. 用 `TaskNode` 替换 task graph 的四字符串记录入口，显式建模 root。
4. 用 `ExecutionEndpoint` 将 executor identity 与对应 `ParName` 成对传递，但 deadlock/purge 仍只按 `ExecutorIdentity` 判定。

这两项可以同一次重构 `TaskEdge`/`TaskGraphData` 时完成，避免两次破坏图 API。

### 第三阶段：有真实扩展需求时再做

5. telemetry 字段扩展时引入 `TaskTiming`。
6. 重新设计 parallelism 显式选择 API，根据重用范围决定是否公开 `ConcurrencyLimit`。
7. 只在 ratio/group ID 真正成为跨模块协议时提取对应值类型。

## 公共值类型的实现约束

项目使用 Java 8，因此不使用 record。新值类型应：

- `final` 且字段全部 `final`；
- 在单一 factory/构造边界验证不变量；
- 显式实现 `equals`/`hashCode`，不依赖对象 identity（`ExecutorIdentity` 是特意建模的例外）；
- 遵守裸 accessor 命名，如 `value()`/`name()`，不引入 `getX()`；
- `toString()` 只用于诊断，不隐式充当持久化协议；
- 仅在真正允许 null 的边界使用 `@Nullable`；
- 不在高频 per-element 路径为了名义类型安全制造大量短命包装对象。

## 最终建议

当前有充分理由立即设计的值类型只有两个：

1. `ParName`：消除公共 API 中逻辑执行入口的 stringly-typed 传播，但不把它宣称为 topology 成员关系的编译期保证；
2. `Deadline`：把结构化并发最核心的 deadline 不变量收口到一个内核类型。

`TaskNode`、`ExecutionEndpoint` 和 `TaskTiming` 都是合理候选，但应与对应模块重构一起引入，而不是单独进行机械包装。其余 primitive 目前保持原样更符合“每个新概念必须证明自己消除了哪类错误”的项目原则。

若需要把“引用已注册”从 submit 时前移到组装期，应评估“未绑定 `TaskGroupDefinition` -> 已绑定 `BoundTaskGroupPlan`”的 typestate API。这是独立于值类型的安全能力，不应通过强制用户定义 enum 间接实现。
